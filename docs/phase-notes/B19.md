# B19 - WebSocket live stream

## What was built

The live view's transport. A short-lived ticket, a socket that catches you up before it streams, and a watcher to prove it works from a terminal.

- `app/services/ws_tickets.py`, `app/services/stream.py`, `app/api/v1/stream.py`, `scripts/ws_watch.py`.
- 52 tests: 13 for tickets, 13 driving a real WebSocket handshake, 19 for replay against real rows, and 7 pinning the fare pattern.

## Key decisions

**A ticket instead of the access token.** A browser cannot set headers on a WebSocket handshake. That leaves the URL or a cookie, and a bearer token in a URL ends up in the server log, the proxy log, the browser history and any `Referer` that leaves the page. So the token stays on an ordinary authenticated POST, and that call hands back a ticket good for one connection in the next minute. A stolen ticket buys one read-only stream of one task, once, within sixty seconds.

**The ticket is redeemed before anything else is checked.** Popped from the store first, then validated. Checking first and popping later leaves a valid ticket lying around after a refused connection, which is a second attempt for whoever guessed wrong about the task id.

**Ownership is checked twice.** At issue time, on a request that carries a real token, and again at connect time. A ticket lives for a minute, and an account can lose its access in that minute.

**Subscribe before reading the database.** The other order has a window between the read and the subscribe where a step is published and seen by nobody: too late for the replay, too early for the live feed. Subscribing first means the worst case is seeing something twice, which deduplication handles, rather than not at all, which nothing can.

**Replayed events carry sequence zero.** The original number is not stored on a step row, and inventing one would break the promise that a task's sequence only goes up. Steps resume on `stepNumber` instead, which is stored, which is why that is the cursor a client sends. A client that wants to track sequence numbers starts doing so when the live feed begins.

**Deduplication is keyed on what is stored.** Steps by number, approvals by id. Those are the only two event types that can arrive from both sides, because they are the only two that are persisted. A status is cheap to repeat and a heartbeat means nothing to compare.

**A finished task gets its replay and a normal close.** Holding the socket open for a task that will never produce another event leaves a client watching a feed that is already over, with no way to tell that from one that is merely quiet.

**One lock around every send.** Three coroutines write to the socket: the event pump, the heartbeat and the reply to a ping. Starlette does not promise that concurrent sends interleave safely, and a torn frame kills the connection.

**Replayed events are excluded from the latency metric.** Their timestamp is when the replay rebuilt them, not when anything happened. Logging that would fill the live-view KPI with numbers that are always near zero and mean nothing.

## Three bugs, and where each came from

**Every WebSocket failed at connect.** The app-state dependencies, which give handlers their settings, database and event bus, all took a `Request`. FastAPI cannot inject a `Request` into a WebSocket route at all, so the socket died before the handler ran, with `TypeError: get_app_settings() missing 1 required positional argument`. They now take `HTTPConnection`, the base class of both. Caught by the first test that opened a real handshake, which is a good argument for testing the transport rather than only the handler.

**The mock read "Apply filters 28 flights" as a fare of 28 rupees.** The currency pattern was `(?:Rs\.?|₹|INR)`, unanchored, and "filters" ends in "rs". The demo run reported ₹28 as the cheapest flight on a page whose cheapest was ₹4,810. A negative lookbehind fixes it, and the test that pins it uses the exact string from the page.

**Truncating extracted text turned ₹5,260 into ₹5.** The cap I added in B16 cut on a character count, and cutting mid-number does not shorten a value, it changes it. The cut now falls back to the last word boundary. Truncation that drops a token is fine; truncation that silently rewrites one is not.

All three came out of running the thing rather than from the tests. The first two only appeared once there was a real site with real text on it, which is what B18 was for.

## Viva questions

**Why is a sixty second single-use ticket better than just putting the access token in the WebSocket URL?**

Because of where URLs end up. A query string is written to the access log of every server and proxy it passes, kept in browser history, and sent in the `Referer` of anything the page loads afterwards. None of those are places a fifteen minute bearer token can be allowed to sit, and none of them are under the application's control.

The ticket narrows what a leak is worth on three axes at once: it works once, for sixty seconds, and only for one task's read-only stream. A leaked access token is every endpoint for the life of the token. The exchange also puts the authorisation on a request that can carry a header properly, which is the part a WebSocket handshake cannot do.

**How do you know replay and live never overlap or leave a gap?**

The gap is closed by ordering: the subscription is opened before the database is read. Anything published after that read lands in the buffer and is delivered when the pump starts; anything published before it is in the rows the replay just read. There is no instant that falls outside both.

That ordering makes overlap possible instead, and overlap is the failure that can be fixed after the fact. A step published between the subscribe and the read appears in both, so the pump skips any step number the replay already sent. The underlying guarantee is the one from B16: a step is committed before it is published, so anything the live feed can carry is already in the database and replayable. If that order were ever reversed, a reconnecting client could be told about a step it can never fetch again, and no amount of deduplication would help.

**The replay loads every missed screenshot from storage. What happens on a task with twenty-five steps?**

It sends about twenty-five images, which at roughly fifty kilobytes each is a megabyte or so in one burst before the live feed starts. That is acceptable for a reconnect and wasteful for a fresh viewer who only wants to see what happens next, and the honest answer is that the current design does not distinguish them.

Two things keep it from being a problem now. A client that was watching passes `after_step`, so it only asks for what it actually missed, and a client attaching to a finished task gets the replay and a close rather than a stream. What it does not do is bound the burst: a client reconnecting from zero on a long task gets everything. The fix is either a cap with a link to fetch the rest by step number, or omitting screenshots from replay entirely and letting the client pull them from the REST endpoint it already has. I left it because the step endpoint exists and is the natural escape hatch, but it is the first thing I would change if a real run showed it.

## Follow-ups

- Tickets and the bus are both per process, so a socket has to land on the worker that issued the ticket and ran the task. Redis is the answer to both, and it is the same boundary.
- `stream_step_latency` is logged and not yet exposed. `GET /metrics` in spec section 6 is where it belongs.
- Replay sends every missed screenshot with no cap. See the third viva question.
- Nothing publishes `recovery` or `approval_resolved` yet, because neither part exists. The event types and the client handling are already in place.
- `scripts/ws_watch.py` uses `websockets`, which arrives with `uvicorn[standard]` rather than being declared. Fine for a demo script; if that extra ever drops it, the script breaks and the service does not.
