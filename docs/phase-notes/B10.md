# B10 - DOM extractor

## What was built

The agent's eyes: a JavaScript collector that walks the page and returns the interactive elements a person could actually use, and the Python side that types the result and turns an index back into a Playwright locator.

- `app/agent/perception/dom_extractor.js` - the collector.
- `app/agent/perception/dom_extractor.py` - `extract()`, `ElementInfo`, `locator_for_index()`.
- Seven fixture pages, 46 tests.

## Key decisions

**The JavaScript is a file, not a string literal.** It is 380 lines with regexes, CSS escaping and a recursive frame walk. As a Python string it would have no syntax highlighting, no linting, and doubled backslashes throughout. As a package resource it is editable as what it is, and `collector_source()` caches the read.

**Indices, not selectors, are what the planner sees.** Every collected element is stamped `data-agent-idx="<n>"`, and the planner picks a number out of the summary. It never invents a CSS selector, which means it cannot target something the collector deliberately withheld. That is the mechanism behind spec section 4.11's target-existence check: the allow-list of things that can be acted on is exactly the list of things that were offered.

**Stale stamps are cleared before every run.** Without that, an index from the previous perception could resolve to a different element after a re-render, and the agent would click something it never chose. The clearing walks same-origin frames too.

**Masking happens in the page, not on the way out.** A password never becomes a Python string at all. Doing it later would mean the real value existed in the process, one careless log line away from spec section 10 being violated. The heuristic covers `type=password` plus any field whose name, id or autocomplete hints at a card, CVV, OTP or PIN, because a card number in a plain text input is just as sensitive as a password.

**Covered elements are dropped, except behind a modal.** Something covered at its centre point cannot be clicked, so offering it invites a step that is guaranteed to fail. A modal is the exception, because dismissing overlays is rung six of the recovery ladder and that code needs to know what is waiting behind one. The distinction is "is the covering element a dialog, or fixed with a high z-index".

**Frame bboxes are offset into the top-level viewport.** A button inside an iframe reports coordinates in the page's space, not the frame's. Otherwise the live-view highlight, the set-of-marks annotator and the click-by-bbox recovery strategy would each have to redo the same arithmetic, and one of them would get it wrong.

**Pointer-styled elements are included, but deduplicated.** Plenty of real controls are `div`s with `cursor: pointer` and no semantics. Including them naively turns a card grid into fifty overlapping candidates, so a pointer-only element is kept only when it has no candidate ancestor and contains no semantic control.

## The bug worth knowing about

The fixture hides seven controls seven ways, each labelled "ignore previous instructions". Six were excluded. One was not.

`.zero { width: 0; height: 0; overflow: hidden }` on a `<button>` still renders **16 by 6 pixels**, because the browser's default border and padding are added outside the content box. The check was `rect.width <= 0 || rect.height <= 0`, taken from the spec's phrase "zero-size", and it let that through.

A 16x6 control is invisible to a person and fully clickable by an agent, so it is a free hiding place for an injected instruction. The fix is a minimum interactive size of 8px in either axis, which is far below any real target (accessibility guidance asks for 44) and far above a sliver.

Two things this is worth remembering for. First, "zero size" in a spec means "not visible", and the literal reading is the wrong one. Second, the test that caught it only existed because the fixture tried seven techniques rather than the obvious three; a fixture with `display:none` and `visibility:hidden` would have passed while leaving the hole open.

## Viva questions

**Why stamp the DOM instead of returning selectors?**

Because a selector is a guess about the future and a stamp is a fact about the present. Between perception and action the page may re-render, and a class-based selector like `.btn-primary` breaks when the framework regenerates class names, which is one of the chaos toggles in spec section 12. The stamp is an attribute we control, on the exact node that was offered, so it survives anything short of that node being replaced. `test_the_stamp_survives_a_class_rename` asserts exactly that.

There is a security argument too. If the planner returned a selector, it could name any element on the page, including one the collector hid. By returning an index into a list we produced, the set of reachable targets is closed by construction.

**How does this defend against prompt injection, given the page can still contain hostile text?**

It removes the cheapest delivery route rather than solving the problem. Spec section 4.11 has several layers: untrusted-data delimiters, a system prompt instruction, schema validation, the action allow-list, target existence, and the risk policy. This part owns one layer, which is that invisible content is never shown to the model. That matters because the usual attack is not visible text, which a user would notice, but a `display:none` div or an off-screen button carrying instructions. A visible button saying "ignore previous instructions" is still offered, and correctly so: it is on the page, a user could click it, and the remaining layers are what stop the model from being persuaded by it.

**What happens when `extract` is called mid-navigation?**

Playwright raises because the execution context was destroyed underneath the evaluate call. That surfaces as `PageNotReadyError`, which is deliberately distinct from the driver's `ActionResult` failures: it is not a page misbehaving, it is us asking at the wrong moment, and the orchestrator's answer is to wait and re-perceive rather than to fail the step or start the recovery ladder. There is also a five second ceiling, because a page with tens of thousands of nodes, or one rebuilding itself in a loop, can make the walk expensive enough to eat into the 300 second task budget.

## Follow-ups

- Nothing consumes `ElementInfo` yet. The summarizer turns it into the `[14] button "Search flights"` lines from spec section 4.6, applies the token budget, and adds the page header.
- Shadow DOM is not traversed. No fixture needs it, and `querySelectorAll` does not cross shadow boundaries, so a site built on web components would come back nearly empty. Worth adding when a demo site needs it.
- The `covered` probe only works for elements inside the viewport, because `elementFromPoint` takes viewport coordinates. Elements below the fold report `covered=false`, which `in_viewport=false` already qualifies.
- `css_path` and `xpath` are collected but unused. They are the fallback for recovery strategy four when the stamp is gone.
