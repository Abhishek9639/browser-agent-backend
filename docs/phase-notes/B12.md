# B12 - LLM adapter base and mock provider

## What was built

The boundary between the agent and any model vendor, and a stand-in model that makes the whole loop testable with no API key.

- `app/agent/llm/base.py` - types, protocol, errors, retry and fallback wrappers.
- `app/agent/llm/mock.py` - `MockLLM`, scripted and rule-based.
- `app/agent/llm/factory.py` - `build_llm`.
- 64 unit tests.

## Key decisions

**One method, and it returns JSON.** `generate_json` is the entire interface. The agent never asks a model for prose, so an adapter that could return free text would be an interface inviting misuse. Narrowing it also makes the mock small enough to trust.

**`LLMBadOutput` is never retried.** This is the most important line in the retry policy. The other three failures mean nothing about the request was wrong, so asking again is reasonable. A malformed answer means the model already saw this exact prompt and produced this exact rubbish; re-sending gets the same rubbish at the same cost. The repair path for that is the planner's single re-ask with the error fed back, per spec section 4.5, and it is a different mechanism because it changes the prompt.

**Full jitter, not fixed backoff.** Without jitter, several concurrent tasks that hit one rate limit retry in lockstep and hit it again together, which is a thundering herd that makes the limit worse. Full jitter picks uniformly from zero to the current ceiling, which spreads them. A test asserts that eight different seeds do not all produce the same delay.

**A server-supplied `Retry-After` wins over the computed backoff.** The provider has told us when to come back; guessing instead wastes the quota we are already short of.

**Retry lives in a wrapper, not in each adapter.** `build_llm` always wraps, so every provider gets the same policy and none can quietly implement its own. It also means the retry policy is tested once against a mock rather than three times against three SDKs.

**Fallback is not retry.** A retry re-asks the same provider because the failure looked transient. A fallback gives up on that provider entirely. They compose, and the distinction matters for `LLMBadOutput`: asking a different model the same question would hide a prompt problem behind a provider switch.

**The mock has two modes because there are two kinds of test.** Scripted is what most tests want, where the test states the decision and asserts on what the loop does with it. Rule-based exists so the whole loop can run end to end, including the flight task from spec section 12, without quota. Neither is clever, and the rule-based one is honest about being a keyword matcher.

**The mock parses the real summary format.** It reads exactly what a model would be shown, so a change to the section 4.6 format that would confuse a real model breaks these tests too. That would not be true of a mock fed structured objects.

## Verifying the mock actually works

The requirement is that rule-based mode can complete the SkyFare task. That is not something a unit test proves, so I wired a throwaway loop against the real fixtures: perceive, ask the mock, execute, repeat.

```
step 1: type     target=To                    value=Bengaluru
step 2: click    target=Search flights
step 3: click    target=Cheapest
step 4: extract  target=the results list
step 5: done     -> "The cheapest option is Rs 4,210."
```

Two things it showed that the unit tests would not have.

It only filled `To`, because the fixture pre-fills `From` and the date. Correct behaviour, and it would have looked like a bug in isolation.

The first run finished with "Nothing further to do on this page" instead of a price. The sort link points at `/results?sort=price`, which the static fixture server answered with a 404, so `extract` returned error text containing no prices. A fixture artefact rather than a mock bug, confirmed by feeding the decision function a realistic history directly. The real demo site will serve that URL. Worth recording because the same shape of failure, an action that appears to succeed while landing somewhere useless, is exactly what the section 4.7 verifier exists to catch.

## Viva questions

**Why does the mock decide from the page rather than keeping a step counter?**

Because a counter would make it a script wearing a rule-based costume. Deriving from the page means the rules advance only when the page really changed, so the mock exercises the same feedback loop a real model would: act, observe, decide again. If a click silently fails, the field is still empty, and the mock tries again rather than marching to step three regardless. It also keeps the mock stateless, so a test can call it with any history in any order.

The one piece of state it does read is the URL, to avoid sorting twice. That is read from the page summary, not remembered.

**The retry wrapper takes `sleep` and `rng` as arguments. Why not patch `asyncio.sleep`?**

Because patching a global for a timing test makes the test depend on the module's internals and on nothing else in the process using `asyncio.sleep` concurrently. Injecting them makes the policy a pure function of its inputs: the test passes a recorder and reads the exact delays back, and a seeded `Random` makes jitter reproducible. It is the same reason `TaskBudget` takes a clock. The production default is the real thing, so nothing is paying for the seam except an argument.

**How does this interact with the token accounting in spec section 9?**

`LLMUsage` carries provider-reported counts, not estimates, and they land on `llm_decisions` alongside the model name, prompt version and latency. That is what makes cost per task and tokens per task real numbers rather than guesses. It is deliberately different from the summarizer's characters-over-four estimate, which is a budget rail that only needs to be roughly right. The mock reports plausible counts so a test asserting on cost has something to read, but nothing depends on those numbers being accurate.

## Known limitations

**Rule-based mode understands one shape of task.** It handles "from X to Y on DATE", a submit button, a sort-by-price control, and prices in rupees. That is the primary demo from spec section 12 and nothing else. It is a test double, not a fallback planner, and it should stay small enough to read in one sitting.

## Follow-ups

- The real adapters, `anthropic.py`, `openai.py` and `gemini.py`, are next. The factory already knows their names and gives a distinct error for "not implemented yet" versus a typo.
- Nothing calls `build_llm` yet; the planner constructs the client and owns the prompt.
- `LLM_FALLBACK_PROVIDER` is wired but untestable against a real outage until there are two real providers.
- A mock in production logs at error level but is not fatal. If that is the wrong call, one line in the factory makes it raise.
