# B25 - Task replay and caching

## What was built

The part that makes the second run of a task cheap, and the first part that can make it wrong if it is built carelessly. Most of the decisions below are about the second half of that.

- `app/agent/cache/signature.py`: `sha256(normalised instruction + start domain)`.
- `app/agent/cache/flow.py`: what a cached step is. A role, a name, the text and a CSS path as a last resort, never an index.
- `app/agent/cache/store.py`: the `FlowCache` over `cached_flows`, including the statistics and the invalidation rule.
- Replay in the orchestrator: cached steps run through the same action building, risk gate and verifier as planned ones, and the first failure hands the page to the planner.
- `GET /tasks/{id}/cache-match` and `POST /tasks/{id}/replay`.
- `CACHE_ENABLED` and `CACHE_MIN_SUCCESS_RATE` settings, and a `--cache` flag on the benchmark.
- 47 tests.

This part opened with the recovery-ladder routing agreed last time, committed separately.

## The measured effect

Same configuration, same four runs, with and without the cache. The first run fills the cache in both, so three of the four are replays in the cached column.

| | uncached | cached |
| --- | --- | --- |
| Cache hit rate | 0% | 75% |
| Tokens in | 2580 | 1272 |
| Estimated cost | 0.0645 INR | 0.0318 INR |
| Median time | 5.3s | 5.1s |
| p90 time | 6.2s | 5.4s |
| Vision calls per step | 0.43 | 0.21 |
| Steps per task | 7.0 | 7.0 |
| Correct answers | 4 of 4 | 4 of 4 |

Half the tokens and half the cost across the four runs. Per run it is larger than that: an uncached run costs about 645 tokens and a replayed one about 209, which is a saving of roughly two thirds on the runs that actually replayed.

Two of those rows are worth reading carefully.

**The time saving is almost nothing here, and that is an artefact.** The mock provider answers instantly, so the wall clock barely moves. Against a real provider the planner is most of a step's latency, and the same replay would save that instead of a rounding error. The token column is the honest one under the mock.

**The vision rate halved because replay never grounds.** A cached step names its target with a locator rather than an index, so there is nothing for visual grounding to correct, and `_replay` does not call it. That removes a screenshot and a vision call per replayed step, which on a real provider is a second saving as large as the planner one.

The step count is unchanged, which is the point: replay does the same work, it just does not ask the model what the work is.

## Key decisions

**The final answer is never cached.** `done` is not stored, so replay can never finish a task by itself. A cached answer would replay last week's price as today's, and the spec cares more about a confident wrong answer than about any other failure, because it is the one a user cannot detect. The consequence is that every replayed run still ends with at least one model call, which is the one call worth paying for.

**A masked value is stored as a marker, not a value.** The collector masks a password or card field at source, so the real value never reaches this layer. The step is kept with `needsPlanner` set, which stops the replay there. Dropping the step instead would produce a flow that silently skips the password field, and storing the mask would type four bullet characters into it.

**Replayed steps go through the risk gate.** A cached sequence can contain a purchase, and a cache that could replay a payment unattended would be the worst thing in this repository. The gate does not care where a decision came from, and the replay path deliberately shares the loop's own code for assessment and approval rather than having its own.

**A replayed step is verified exactly like a planned one.** It is evidence that something worked once, which is worth less than it looks: the page may have changed underneath it. The verifier is what decides, and a replayed step carries the same expected outcome that the original step was checked against, rather than falling back to its action's default.

**A replayed step writes no `llm_decisions` row.** That absence is the audit trail. Counting steps without a decision row is how the saving is provable after the fact rather than only visible in a log while the run is happening.

**Normalisation removes only what cannot change the meaning.** Case, surrounding and repeated whitespace, unicode width, trailing punctuation. Nothing inside the sentence: "to Delhi" and "from Delhi" must stay different signatures, which rules out stemming and stop-word removal. Those would raise the hit rate by occasionally replaying a flow for a different task, and a cache that is sometimes wrong is worse than one that sometimes misses.

**The port is not part of the key, the host is.** A demo server on a fresh port every run would otherwise never hit its own cache. The trade is that two services on one host share a keyspace, which is acceptable for a start domain and would not be for a full URL.

**Invalidation deletes the row.** Below half after at least three runs, it goes. Keeping it as a flag would mean every task with that signature pays for the lookup forever to be told the same answer. Three runs is the spec's number and it is the right shape: below that the rate is an opinion, not a measurement.

**Success for a flow is stricter than success for the task.** A run counts as a success for the flow only if every cached step replayed and verified with no fallback. A flow that needs rescuing every time is not worth replaying even when the task around it completes, and scoring it by the task's outcome would keep a useless flow alive indefinitely.

**Replay is bound through `tasks.cache_flow_id` rather than a new column.** A task that already names a flow when the run starts is a forced replay, which is exactly what the replay endpoint creates. No migration, and the row reads honestly either way: it says which flow this task used.

**`POST /replay` creates a new task.** The finished one is the record of what happened, and re-running it in place would overwrite the history somebody is looking at.

## A bug this part found

Replaying more than one step failed with `Cannot move a task from VERIFYING to ACTING`. The loop returns to `PLANNING` at the end of every iteration, so `ACTING` is only ever entered from `PLANNING`, and the replay path had no planning phase to return to. Fixed by tracking the phase through the replay and moving back to `PLANNING` between steps: the decision comes from the cache rather than from the model, but deciding is still the phase it happens in, and the state machine models the loop.

It was caught by the chaos test rather than by the unit tests, because the unit rig replays a single step and the transition is only illegal from the second onwards.

## Viva questions

**What stops the cache from making the agent confidently wrong?**

Three things, in order of how much they matter.

The answer is never cached, so no run can report a stale result. The `done` step is excluded when the flow is stored, which means a replay always ends by handing the live page to the planner and asking it what the answer is.

Every replayed step is verified by the same deterministic verifier, against the same expected outcome the original step passed. A cached step is a suggestion about where to click, not a claim that clicking there still works.

The locator is re-resolved on the live page and can simply fail to resolve, which ends the replay before anything is executed. That is the common case for a stale flow, and it costs the run one lookup.

The residual risk is a locator that resolves to the wrong control: a page that keeps a CSS path and changes the button behind it. The CSS path is the last rung for that reason, and the verifier is what catches the consequence.

**Why is the success rate updated even when the task completed?**

Because they are different questions. The task's outcome says whether the user got their answer; the flow's rate says whether replaying it was worth doing. A flow whose first step no longer resolves produces a perfectly good task every time, via the planner, and replaying it is pure overhead. Scoring the flow by the task would keep that flow at a hundred percent forever.

Three runs below half and the row is deleted, so a flow that has genuinely gone stale stops costing anything within three attempts.

**A user replays a task from six months ago. What happens?**

The endpoint binds a new task to the stored flow and queues it, ignoring the success rate, because the user asked for this sequence rather than for the cache's opinion of it.

The run then almost certainly falls back early: six months of site changes mean the stored roles and names no longer resolve, and the replay stops at the first step it cannot find. The remaining steps go to the planner as a hint, phrased as what a previous run did, and the prompt already tells the planner a hint describes what worked before and has to be checked against the page in front of it. The task completes normally, having cost one lookup more than a fresh run.

What the user gets that they would not from submitting the instruction again is the binding: the new task records which flow it replayed, and the flow's statistics record that the replay failed, which is what eventually removes it.

## Follow-ups

- The chaos suite and the default benchmark run with the cache off, deliberately: a replayed run does not exercise the planner or the ladder, so caching them would stop the recovery numbers meaning anything. `--cache` measures the cache instead, into its own report file.
- **Known limitation: the cache is shared across users.** A flow is stored per signature, so two users solving the same instruction on the same site replay each other's. The sequence itself is not secret, but "somebody has already solved this exact instruction" is an inference a stranger should not be able to draw, and `cache-match` exposes it directly: a run count above zero for an instruction you have never submitted says someone else has.

  Single user is the scope of this project, so it is recorded rather than fixed. The fix, when this goes multi-tenant, is to put the user id into the signature material alongside the instruction and the start domain, which partitions the keyspace per user and needs no schema change: the column holds a hash either way. A deployment that wants sharing back can then make it an explicit setting rather than an accident of the key.
- The CSS rung can resolve to a control the flow never meant, on a page that reuses a selector for a different button. The verifier catches the consequence rather than the cause, and there is a test that states this plainly rather than pretending otherwise.
- Nothing prunes flows that are never used. Invalidation only fires on a replay, so a flow for an instruction nobody repeats sits in the table forever.
- `run_count` counts replays, not stores. A flow stored ten times and replayed twice reports two runs, which is the number that matters for the threshold but reads oddly next to the timestamps.
