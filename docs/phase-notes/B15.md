# B15 - Task state machine and event bus

## What was built

The two pieces that sit between the agent loop and everyone watching it. The state machine decides what a task is allowed to do next; the event bus is how anyone outside the loop finds out that it did.

- `app/domain/state_machine.py` and `app/services/events.py`.
- `docs/agent.md`, with the lifecycle as a Mermaid state diagram.
- 106 unit tests.

Neither has a caller yet. The orchestrator drives both, and the WebSocket route consumes the bus.

## Key decisions

**The transition table is written out, and the test writes it out again.** The test does not derive its expectation from `TRANSITIONS`; it restates the table by hand from spec section 4.3. A test that recomputes the thing it is checking agrees with any bug you introduce. Restating it means a change to the lifecycle has to be made deliberately in two places, which is the friction I want on something that decides whether credits get settled.

**`ACTING` cannot reach `COMPLETED`.** This is the single most load-bearing row. Spec section 4.7 exists because the agent must not take its own word for an outcome, and the table is where that stops being a convention: an answer can only be declared from `VERIFYING`, or from `PLANNING` where the planner decided the goal was already met without touching the browser. Without the table, a shortcut here would surface as a confidently wrong answer rather than an error.

**`CANCELLED` and `TIMED_OUT` are composed in rather than listed.** They are reachable from every live status and from no terminal one. Writing them into each row would be eleven chances to forget one; a set unioned into every non-empty row cannot be forgotten. Terminal rows stay empty, so a finished task cannot be cancelled and a failed one cannot be retried in place, which matches spec section 6 making a replay a new task row.

**An illegal transition raises.** A silent no-op would leave a task in a state nobody chose while the loop carried on regardless, and the symptom would appear somewhere else entirely. The error message lists what *was* allowed, because the reader of that traceback is trying to work out which of two things is wrong: the caller, or the table.

**`transition` returns the previous status.** The section 6.1 `status` event carries both. Returning it means the caller cannot forget to capture it before the assignment, which is exactly the kind of thing that gets forgotten once and then produces a `previousStatus` equal to `status` forever.

**Events are frozen.** The same object is handed to every subscriber. One consumer mutating it would rewrite another consumer's history, and it would do so intermittently, depending on which subscriber ran first.

**`seq` is assigned by the bus, not the publisher.** A publisher does not know its own sequence number, because ordering is a property of the task's stream rather than of any one producer. `publish` returns the stamped copy so the caller can persist what was actually sent.

**Two budgets for load shedding, not one.** The brief says drop older step screenshots first. My first version did exactly that and was wrong in a way worth recording: stripping a screenshot frees memory but not a queue slot, so under a steady stream of steps with screenshots the buffer grew without bound while dutifully stripping images. Splitting it into a screenshot budget and an item budget, with the screenshot budget much the smaller, gives the policy the brief asked for *and* an actual bound. Images go first because they are a hundredfold more expensive than the event carrying them, and because a step without its thumbnail still renders in the activity log and the image is refetchable by step number.

**Some events are never dropped.** Losing a `status`, `approval_required`, `approval_resolved`, `final` or `error` leaves the client permanently wrong rather than merely behind: a badge that never updates, a human who is never asked, a spinner that never stops. If the queue holds nothing else, the bound gives way and a warning is logged. Too much memory is a bad day; a client stuck on the wrong status is a wrong product. An approval also keeps its screenshot: somebody being asked to approve a purchase is entitled to see what they are approving.

**`EventBus` is an abstract base class, and the in-memory implementation is honestly limited.** It fans out within one process, so with more than one worker a client on A never sees events published on B. That is a real limitation, not a rough edge, and it is the reason the interface exists: a Redis pub/sub implementation drops in behind it, taking its sequence numbers from `INCR`.

## Three things I changed after testing them

**A convenience iterator that leaked.** I had written a `stream()` async generator alongside `subscribe()`. A test of the case that actually happens in production, a client disconnecting mid-run, showed the subscription still registered afterwards: breaking out of an `async for` over a generator leaves cleanup to generator finalization, which the event loop schedules whenever it gets round to it. Until then the subscription keeps receiving events into a buffer nobody reads. `subscribe()` as an async context manager already does this deterministically, so I deleted `stream()` rather than keep a second way out with worse semantics. One supported way is better than a convenient one and a correct one.

**The buffer bound that was not a bound.** Described above. It was the test that made it obvious: I could not write an assertion about how much was queued, because the answer was "it depends how long the run is".

**A lock I checked rather than assumed.** I mutated `publish` to drop the lock and the concurrency test still passed, because the critical section has no `await` in it and is therefore already atomic on a single event loop. Rather than keep a lock on faith or delete it on a technicality, I mutated again with an `await` inserted mid-section: without the lock the test fails, with it the test holds. So the lock is not protecting today's code, it is protecting the invariant against the first `await` somebody adds, which a Redis `INCR` certainly will. That is worth keeping, and now the comment says so instead of overstating it.

## Viva questions

**Why enforce the lifecycle in a table at all, when the orchestrator knows perfectly well what it is doing?**

Because "the orchestrator" is not one place. Status gets written by the runner advancing a step, by the approval endpoint when a human answers, by the cancel endpoint, by the timeout sweeper, and by whatever handles a crashed browser. Each of those knows its own move is legal; none of them knows what the others might have done in between. The table is the only component that sees every edge at once.

The concrete failure it prevents is a race: a user cancels while a step is in flight, the step completes, and the runner writes `COMPLETED` over `CANCELLED`. With the table, that second write raises instead, because nothing leaves a terminal state. Without it, the user is told their cancelled task succeeded, and has been charged for it.

**A dropped event is invisible to the client. How does anyone find out it happened?**

Three ways, deliberately, because one is not enough. Each subscription counts `screenshots_stripped` and `events_dropped`, so the WebSocket route can log what a session cost on the way out. Shedding that reaches the undroppable case logs a warning with the task id, because at that point something is badly wrong with that client. And the client can tell on its own: `seq` is strictly increasing per task, so a gap between consecutive events is a dropped event, and the client knows to refetch rather than assume it has the full history.

That last one is the real answer to why sequence numbers are worth the bookkeeping. Without them a client cannot distinguish "nothing has happened" from "I missed something", and shedding load silently would be indistinguishable from lying.

**Why is `AWAITING_APPROVAL` a persisted status rather than something the UI infers from an open approval row?**

Because inference and truth drift apart at exactly the wrong moment. If the status stayed `ACTING` while an approval was pending, then a reconnecting client, a task list query, and the timeout sweeper would each have to join to `approvals` and reimplement the same rule, and the first one to get it slightly wrong shows a user a task that is apparently running while it has in fact been waiting on them for an hour.

Making it a status also makes the rules enforceable in the one place that already enforces rules. `AWAITING_APPROVAL` leads to `ACTING` or `REJECTED` and nowhere else, so there is no path that walks around the gate, and an unanswered approval expiring to `TIMED_OUT` is the same mechanism as any other budget expiring rather than a special case. Decision A3 made the same call for `RECOVERING` and `VERIFYING`, for the same reason: what the live stream shows and what a reconnecting client sees have to be the same thing.

## Follow-ups

- Nothing calls either module yet. The orchestrator owns both.
- Heartbeats are modelled but nothing emits them; the cadence belongs with the WebSocket route.
- The in-memory bus is single-process. A Redis implementation is needed before running more than one worker, and it is the point at which `seq` should come from `INCR`.
- `transition` logs the change but does not persist it. Writing the row and publishing the `status` event are the orchestrator's job, in that order and in one transaction.
