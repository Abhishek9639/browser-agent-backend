# B13 - Anthropic, OpenAI and Gemini providers

## What was built

Three real adapters behind the interface from the previous part, so the planner can talk to a model without knowing which one.

- `app/agent/llm/anthropic.py`, `openai.py`, `gemini.py`.
- Per-provider API keys with a startup check.
- `scripts/llm_smoke.py` and a `live` test marker.
- 38 unit tests, none of which call a real API.

## Key decisions

**The API shapes were looked up, not recalled.** The brief asked for this and it was the right call: all three surfaces have moved. OpenAI structured output is `client.responses.create(text={"format": {...}})`, not `chat.completions` with `response_format`. Anthropic is `output_config={"format": {"type": "json_schema", "schema": ...}}`, not the older `output_format`. Gemini takes `response_json_schema` alongside `response_mime_type`, which accepts a raw JSON Schema directly rather than going through a Pydantic conversion. Token usage field names differ again, and those I read off the installed SDK types rather than any document, because that is the only source that cannot be out of date relative to the code actually running.

**The SDKs' own retries are switched off.** Each client is constructed with `max_retries=0` because `RetryingLLM` already owns that policy. Two independent retry layers do not add resilience, they multiply: three of ours times three of theirs is nine calls and nine times the cost for one logical request, with backoff behaviour nobody can reason about.

**A 4xx that is not 429 raises the base `LLMError`.** `is_retryable` only matches timeout, rate limit and unavailable, so a bad key, a bad model name or a malformed request is not retried. Retrying would re-send the same broken request three times before failing with the same message. `FallbackLLM` still moves to the second provider for these, which is right: a misconfigured primary is exactly when a fallback earns its place.

**Only sizes and counts are logged.** Spec section 10 forbids logging page content, and both the prompt and the answer are derived from it: the prompt carries the page summary, the answer carries a target description lifted from the page. The log line has provider, model, token counts and an image count, and a test records the logger and asserts the page text never appears in what it was handed.

**Fenced JSON is tolerated.** Schema enforcement means this should not happen, but models wrap JSON in markdown however firmly the prompt says not to, and failing a step over three backticks would be a poor trade. Anything else malformed is `LLMBadOutput`, which is never retried at the transport layer and goes to the planner's single repair re-ask instead.

## The redaction rule bit again

The first run logged `input_tokens=[REDACTED]`. The masking rule matches any key containing "token", and it had eaten the token counts, which is the opposite of useful: those numbers are the cost metric in spec section 9.

In the earlier part the same problem was solved by renaming the field (`token_id` became `session_id`). That will not work here, because `input_tokens` and `output_tokens` are the column names in `llm_decisions`. Renaming to dodge our own filter would leave the log and the schema disagreeing.

So `app/core/redaction.py` gained `SAFE_KEYS`: a small **exact-match** allowlist of keys that contain a sensitive-looking word but are always measurements. Exact match, never a substring, and the comment says the only thing that may be added is a count or a size. `access_token`, `refresh_token` and `token_hash` still mask, and there are tests for both directions.

Worth noting as a pattern: a broad security rule earns its breadth, but it needs a narrow, explicit, tested escape hatch, or people start renaming their data to get around it.

## Running the live smoke test

Nothing in `make check` calls a real API. To check a provider end to end with your own key:

```bash
# Anthropic
LLM_PROVIDER=anthropic ANTHROPIC_API_KEY=sk-ant-... uv run python scripts/llm_smoke.py

# OpenAI
LLM_PROVIDER=openai OPENAI_API_KEY=sk-... uv run python scripts/llm_smoke.py

# Gemini
LLM_PROVIDER=gemini GOOGLE_API_KEY=... uv run python scripts/llm_smoke.py
```

It sends one text prompt and one image prompt (a 64x64 red square generated in-process) and prints the parsed JSON, token counts and latency for each. `--skip-image` sends only the text one. Cost is a few hundred tokens.

`LLM_MODEL` selects the model and must be one that provider recognises. The live pytest test is the same idea inside the suite:

```bash
LIVE_LLM=1 LLM_PROVIDER=anthropic ANTHROPIC_API_KEY=sk-ant-... uv run pytest -m live
```

**Verified against Gemini**, `gemini-3.6-flash`: both the text and the image prompt returned valid parsed JSON, with token counts and latency recorded. That is the first end to end confirmation that a real provider works through this layer, images included. The project's `.env` now runs `LLM_PROVIDER=gemini` with that model.

## Viva questions

**Three providers, three different ways of constraining output. What is actually the same?**

The guarantee we build on, which is that the response parses as an object matching our schema. Anthropic and OpenAI enforce it server-side, OpenAI additionally with `strict: true`, and Gemini enforces it through `response_json_schema` with a JSON mime type. Underneath, each is doing constrained decoding against the schema. What differs is only the parameter name and nesting, which is exactly the kind of detail an adapter exists to absorb. The planner sees `generate_json(system, messages, schema)` and a `dict` back, and would not change if a fourth provider arrived.

The honest caveat is that schema enforcement is not the same as correctness: the model can return a perfectly schema-valid decision naming an element index that does not exist. That is why the target-existence check in spec section 4.11 sits after this layer, not instead of it.

**Why does each adapter map SDK errors instead of letting the planner catch the SDK's own?**

Because otherwise every layer above would need to know all three SDKs. The recovery ladder would be matching on `anthropic.RateLimitError` *and* `openai.RateLimitError` *and* Gemini's `APIError` with `code == 429`, and adding a provider would mean touching all of them. With the mapping, `RetryingLLM` asks one question, `is_retryable`, and the orchestrator sees four error types no matter what is underneath. It also means the retry policy is tested once, against a mock, rather than three times against three vendors' exception hierarchies.

**How would you test any of this without spending money?**

Every test injects a fake client through the adapter's `client=` argument, which exists for exactly that. The fakes implement only the surface the adapter touches, roughly ten lines each, and they record the request so the tests can assert on what was actually sent: that the schema reached `output_config.format.schema`, that an image arrived base64-encoded with the right media type, that the timeout was passed through. That is the part worth testing, because it is the part that breaks when an SDK changes. The live tests exist for the other half, whether the provider accepts what we send, and they are marked and skipped by default so CI never depends on a vendor being up or on a key being present.

## Planned optimisation: prompt caching

**Decided, not yet implemented.** Every step of a task sends the same system prompt and the same action schema; only the page summary and the history change. That is exactly the shape prompt caching is built for: a long stable prefix followed by a short volatile suffix.

On a twenty-five step task the saving is most of the prefix, twenty-four times over. It also needs care rather than a flag, because caching is a prefix match: the stable content has to come first and the volatile page summary last, or the cache is invalidated on every step and the change achieves nothing but complexity.

Not done here because the planner owns the prompt and does not exist yet. It belongs in the part that assembles it, where the prefix and suffix boundary is a design choice rather than a retrofit. Each provider exposes it differently, so it goes behind the adapter interface like everything else.

## Follow-ups

- `LLM_MODEL` is a single setting shared by all providers, so switching provider means also changing the model name. A per-provider default would be friendlier.
- `LLM_VISION_MODEL` is defined but unused; the adapters send images to `LLM_MODEL`. Wiring it belongs with the grounding step that actually needs vision.
- No streaming. The planner wants one complete JSON object, so there is nothing to stream to, but a long decision could approach a request timeout on a slow provider.
