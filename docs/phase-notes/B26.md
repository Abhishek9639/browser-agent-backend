# B26 - Chaos suite and benchmark runner

## What was built

The two things that turn "it worked when I tried it" into a number. The chaos suite is the definition of a passing run; the benchmark is the same runs counted.

- `tests/chaos/`: harness, conftest and the suite itself, ten configurations.
- `scripts/benchmark.py`, `make chaos`, `make bench`.
- `docs/benchmarks/2026-09-27-mock.md`, the first report.
- Visual grounding's acceptance floor now depends on which trigger fired.

## Key decisions

**The suite and the benchmark share one harness.** A benchmark measuring something slightly different from what the suite asserts would produce numbers nobody could act on, and the suite is where "passing" is defined. One `run_once`, used by both.

**The contract is "answer correctly or fail readably", not "always succeed".** Some of these configurations are genuinely hard and giving up with a reason is an acceptable outcome. What is never acceptable is completing with the wrong number, because a wrong answer delivered confidently is the single failure a user has no way to detect. Every configuration asserts that; the easy ones additionally have to succeed.

**Success means the number matches the oracle.** Not that the task reached COMPLETED. The agent reports a sentence and the oracle reports a fare, so the comparison is on the digits: a run that finishes happily with the second-cheapest flight is a failure, and counting it as a success would make the headline metric meaningless.

**The HTTP API is not in the chaos path.** It is covered by the integration suite. Putting it here would mean a chaos failure could be a routing bug, and the whole point of a chaos suite is that a failure tells you which of the agent's defences did not hold.

**Recovery rate is per failure, not per attempt.** The first report said 36% and failed the target. That was the metric being wrong rather than the agent: the ladder tries several rungs to fix one failure, so counting rungs scores a step rescued on the third attempt as two failures and one success. Spec section 9 asks for recovery success on induced failures, which is a rate per failure. Grouped by episode it is 80% on the same runs. Reporting FAIL on a number measured the wrong way is worse than not reporting it at all.

**The mock is the default for both.** A suite that spends money whenever somebody types `make chaos` is a suite people stop running. `--live` opts in.

**Prices are settings.** Cost per task is derived from `LLM_PRICE_INPUT_PER_MTOK` and friends rather than a table in the script, because a number hardcoded in a benchmark is a number nobody updates and everybody eventually quotes.

**Grounding's acceptance floor depends on the trigger.** A correction is nearly free when the planner said it had no idea, or when the recovery ladder has exhausted everything that works by name. It is expensive when the planner chose a specific element and vision was called only because two elements share a label: there the planner may well be right, and overruling it on a 0.5 reading swaps a good target for a bad one. The floors are 0.0, 0.35 and 0.7 depending on why grounding ran.

## What the first benchmark says

Thirty runs, three per configuration, mock provider. End-to-end success 90% against a target of 80%, recovery 80% against 70%, verification accuracy 99%, median 5.7 seconds per task.

The one failing configuration is `iframe`, and it fails for a reason already known: the driver resolves selectors with `page.locator`, which only searches the main frame, so results rendered inside an iframe are perceived but cannot be acted on. `locator_for_index` already walks every frame; wiring the driver to it is the fix, and it was noted as a follow-up when the loop was built. The benchmark has now put a number on it.

The p90 of roughly 49 seconds is almost entirely the cookie configurations, where a failed recovery rung waits out the ten second browser timeout before the rung that works gets its turn. That is the same cost recorded after the first end-to-end demo, and routing the ladder by the failure's error code is the fix.

## Viva questions

**Why is "completed with the wrong answer" a failure rather than a partial success?**

Because of who can detect it. A task that fails tells the user it failed: they can retry it, read the reason, or do it by hand. A task that completes with the second-cheapest flight looks exactly like a task that completed correctly, and the only way to find out is to do the work the agent was supposed to do. The cost of the two errors is not comparable, so a metric that averages them hides the one that matters.

That is also why the demo site has an oracle the agent cannot reach. Without ground truth the only available check is whether the agent thinks it succeeded, which is the thing being measured.

**The suite runs in one process with a real browser. Why not mock the browser and make it fast?**

Because every configuration here is a thing a real browser does and a fake one does not. A cookie banner intercepting a click, an element that is perceived but covered, a page still rendering when it is read, an iframe that a selector does not reach: all of those are properties of a real DOM and a real Playwright. Mocking them would mean asserting that the agent handles a model of the problem, which is how you end up with a suite that passes while the agent does not work.

The cost is real. The suite takes about six minutes and needs Postgres and a browser, so it is not in `make check`. That is the right trade for something that runs before a release rather than on every save.

**A benchmark with one run per configuration is a small sample. What is it actually good for?**

Regression detection more than measurement. Thirty runs cannot distinguish an 85% agent from a 90% one, and the report should not be read as if they could. What it does reliably catch is a configuration that used to work and now does not, which is the common failure when a change to perception or recovery has an effect nobody predicted.

For an actual measurement the run count has to go up, which is what `--runs` is for, and the per-configuration table matters more than the headline: knowing that `iframe` fails every time and everything else passes every time is far more useful than knowing the average is 90%. A single aggregate over ten unlike configurations is a number that sounds informative and is not.

## Follow-ups

- `iframe` is the one failing configuration and the fix is known: resolve selectors through `locator_for_index`, which already walks every frame.
- The ladder spends ten seconds on each rung that cannot work. Routing by the failure's error code is the fix, and it is queued.
- Vision figures are meaningless under the mock: it answers with a planner-shaped payload, grounding correctly declines, and the tally records three failed calls per run. That is the right degradation path and the wrong thing to measure. A live benchmark would give real numbers.
- Approvals and cache hits are always zero because neither part exists yet. The columns are there so the report does not change shape when they do.
- The benchmark writes to the test database and leaves its rows behind. Fine for a benchmark; worth a cleanup flag if it ever runs often.
