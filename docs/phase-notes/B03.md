# B03 - Postgres, async database layer, Alembic

## What was built

Postgres in compose, an async SQLAlchemy layer over it, Alembic wired to the same settings the app uses, and a health endpoint that tells the truth about whether the database is reachable.

- `docker-compose.dev.yml` with postgres:16, a named volume, a `pg_isready` healthcheck, and an init script creating `agent_core`, `agent_core_test` and `payments`.
- `app/db/base.py` - `Base`, the constraint naming convention, `UUIDPrimaryKeyMixin`, `TimestampMixin`.
- `app/db/session.py` - `Database`, the session context manager, `healthcheck()`, and the FastAPI dependencies.
- `migrations/` on the async template, baseline revision `0001_baseline`.
- Health now reports `db` and returns 503 when Postgres is down.
- 51 unit tests, 10 integration tests.

## Key decisions

**One set of credentials, derived two ways.** compose needs `POSTGRES_USER` and friends; the app needs a DSN. Declaring both independently is how a `.env` ends up with a password the container does not have. Instead `Settings` owns `POSTGRES_*` and derives `database_url` and `test_database_url` from them, and compose reads the same variables out of `.env`. `DATABASE_URL` survives as an override for a managed instance. The DSN builder runs the user and password through `quote_plus`, so a password containing `@` or `/` does not silently corrupt the URL.

**The engine lives on `app.state`, not at module scope.** Same reasoning as settings in B02. `Database` is constructed in the lifespan, disposed in the reverse-order teardown, and reached through `get_database(request)`. A unit test overrides that dependency with a stub and never opens a socket, which is why `make check` needs no Docker.

**Alembic takes its URL from `Settings`, and `alembic.ini` is left blank.** A URL written into the ini file is a second source of truth, and the failure mode is a migration applied to the wrong database. `env.py` calls `get_settings()` and sets the option at runtime. `alembic.ini` carries a comment saying why it is empty.

**`make revision` formats what Alembic generates.** The stock `script.py.mako` emits `from typing import Sequence, Union` and `Union[str, ...]`, which our ruff rules reject, and a `Revises: ` line with trailing whitespace on the first revision. Fixing the one generated file would have left the next twenty broken, so the template itself was rewritten and the `Revises:` line made conditional. Alembic still renders string literals with `repr()`, giving single quotes that ruff-format rewrites, so the `revision` target runs `ruff format` afterwards. `F401` is ignored under `migrations/versions/` because Alembic always imports `op` and `sa` whether a revision uses them or not.

**A baseline revision with no schema.** There are no models yet, so `0001_baseline` does nothing. It exists so `alembic_version` is created, `make migrate` is meaningful today, and the revision that adds the nine tables has a parent to point at rather than being the root.

**Tests roll back rather than truncate.** The per-test session binds to a connection with an open transaction and uses `join_transaction_mode="create_savepoint"`, so a test can call `commit()` and still be undone. `test_each_test_starts_clean` asserts the previous test's row is gone, which makes the isolation an actual assertion rather than an assumption.

## Environment note

Port 5432 on this machine was already held by a Homebrew Postgres 14 bound to `127.0.0.1`, which shadows Docker's wildcard bind: `docker exec psql` worked while the app got `role "postgres" does not exist`, because it was reaching a different server. `POSTGRES_PORT=5433` in the gitignored `.env` moves the published port, and since compose and the app read the same variable they stay in agreement. The committed default stays 5432, per spec section 2. Documented in the README.

## Viva questions

**Why does the health endpoint return 503 rather than 200 with a status field?**

Because something automated reads it. Docker's healthcheck, a load balancer and Kubernetes all decide from the status code whether to route traffic to this instance, and they do not parse the body. A process that is up but cannot reach Postgres cannot accept a task, so reporting 200 would keep sending it work it is guaranteed to fail. The body still carries the detail, `{"db": "down", "status": "degraded"}`, for a human or a dashboard. Note it deliberately returns the health payload rather than the error envelope: a probe wants the diagnostic fields, not an error code.

**Why is a constraint naming convention worth setting up before there are any tables?**

Alembic's `--autogenerate` works by diffing the model metadata against the live schema. If a constraint has no explicit name, Postgres invents one such as `_test_sample_rows_label_key`, while SQLAlchemy's metadata has `None`. The two never compare equal, so every autogenerate run proposes dropping and recreating constraints that have not changed. Setting the convention on `MetaData` means both sides agree by construction. It has to be done before the first table exists, because changing it later means renaming every constraint already in the database. `test_constraint_names_follow_the_naming_convention` asserts the real names Postgres reports.

**What does `join_transaction_mode="create_savepoint"` do, and why not just truncate tables between tests?**

The fixture opens a connection, begins a transaction, and hands the session a connection that is already inside one. Without that setting, a `session.commit()` in the test would commit the outer transaction and the data would persist into the next test. With it, SQLAlchemy turns each commit into a savepoint release, so the code under test can commit normally while the outer transaction still rolls everything back at teardown. Truncating instead would be slower, would reset sequences, and would not protect against a test that leaves a transaction open. The rollback approach also means tests can run against a schema created once per session rather than per test.

## Follow-ups

- `app/models/` is still empty; `migrations/env.py` imports it already, so the nine tables from spec section 5 need only be imported there.
- `updated_at` uses SQLAlchemy's `onupdate`, which is client-side. A raw `UPDATE` will not touch it. If that becomes a problem, the fix is a Postgres trigger.
- `app/repositories/` is untouched. The `get_session` dependency is what they will take.
