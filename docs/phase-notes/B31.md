# B31 - Architecture, ADRs, traceability and the v1.0.0 release

## What was built

The documentation part, and the tag. Nothing in `app/` changed except two test
docstrings.

- `docs/architecture.md`: five Mermaid diagrams with prose, marking implemented against future work.
- `docs/adr/`: twelve ADRs and an index.
- `docs/traceability.md`: BR and FR ids to modules, tables and real test names, with the gaps flagged.
- `docs/api.md` and `docs/openapi.json`, generated from the running application.
- `docs/viva-prep.md`: 90 questions in three tiers.
- `README.md` rewritten, `docs/RELEASE_NOTES_v1.0.0.md`, tag `v1.0.0`.

## Generated rather than written, wherever possible

Four of these documents are produced from the code rather than typed beside it,
because a document that is typed is a document that goes stale silently.

`docs/api.md` and `docs/openapi.json` come from `app.main.create_app().openapi()`,
so every endpoint, parameter and status code is the one the application actually
serves. The WebSocket event samples are generated by constructing each event model
and dumping it, so the JSON in the document is the shape a client receives rather
than one I remembered.

`docs/viva-prep.md` extracts all 90 questions and answers from the phase notes
with a script. The answers are unchanged: they were written while each decision
was fresh and its alternatives were still on the table, and rewriting them now
would have smoothed away the reasons.

The state machine diagram in `docs/architecture.md` is checked against
`app/domain/state_machine.py` edge for edge: nothing in the code is undrawn and
nothing drawn is invented.

## The accuracy pass, and what it found

The acceptance asked for a final pass listing any mismatch fixed. Five, four of
them stale names that no test would ever have caught:

1. **`docs/traceability.md` cited `test_a_cancel_stops_the_loop_at_a_phase_boundary`.** No such test. It is `test_a_cancel_between_iterations_stops_the_loop`.
2. **ADR-004 cited `test_the_verifier_never_calls_a_model`.** It is `test_the_verifier_never_reaches_for_a_model`.
3. **`docs/architecture.md` referenced `app/agent/perception/collector.js`.** The file is `dom_extractor.js`. The same wrong name was in `docs/security.md` and was fixed during B28, which means I made it twice from the same bad memory of the spec's table.
4. **The README claimed 1,147 unit tests.** That is how many pass; 1,148 are collected and one is skipped. Now stated as both.
5. **TEST-004 and TEST-005 had no citation in any test.** Both were genuinely covered — the planner's happy path and the recovery-attempt assertions in the integration orchestrator test — but neither test named the id, so the mapping existed only in my head and would have existed only in a document. The ids are now in those two docstrings, which makes all ten greppable.

The first four were found by a script that extracts every `file::test_name` and
every module path from the new documents and checks each one exists. That script
is the reason this pass found anything; reading the documents again would not
have.

## Key decisions

**The BR and FR numbering is assigned here, and the document says so.** The
consolidated specification cites exactly two ids by name — `BR-008` for
human-in-the-loop approval and `ADR-004` — and decision A18 already settled that
the specification's text is the whole requirement. So BR-008 is pinned to the
requirement it names, ADR-004 is written to the decision it names, and everything
else is derived from the specification's own text and labelled as assigned rather
than quoted. Inventing a provenance would have been worse than admitting the
numbering starts here.

**Requirements without a test are listed, not omitted.** Six of them: the payments
integration has no test against a real payments service, the prompt eval cannot
distinguish prompt versions, no test asserts a vision model picks the right mark,
shadow DOM is untraversed, the section 9 KPIs are measured under the mock, and a
WebSocket frame has no size limit. A traceability matrix with no gaps is a
traceability matrix nobody checked.

**The viva answers are grouped by breadth, not by difficulty.** A beginner
question is answerable from one file; an advanced one needs a failure mode. The
advanced tier is the one to read, because those are the questions where the answer
is a decision rather than a fact.

**The disclaimer is specific.** "Student project, use at your own risk" would have
been shorter and said nothing. It names the five things that actually matter: no
real transactions, only automation-permitted sites, no CAPTCHA bypass and none of
the twelve actions can solve one, no real personal data, and not hardened for
deployment.

## The live benchmark

Run as instructed: `--provider gemini`, five runs of the primary configuration,
no retry. It produced no usable measurement. `gemini-3.6-flash` answered every
request with `503 "This model is currently experiencing high traffic"`, so all
five runs failed with `LLMUnavailable` — one after a single step, four before any.

Not rate limiting, which is what was expected: a 503 from the model's own
capacity rather than a 429 against the key's quota. The report is kept, with a
note at the top stating that its 0% end-to-end success is a fact about provider
availability at 09:32 on 2026-09-29 and not about the loop.

What it does show is worth keeping. A provider that fails every call produces five
clean failures with a readable reason, no crash, and verification accuracy intact
on the one step that ran. That is the degradation path from ADR-007 and TEST-010
working under a condition nobody arranged.

## Viva questions

**Why generate the API documentation instead of writing it?**

Because the alternative decays and nothing tells you. An endpoint gains a
parameter, a status code changes, a field is renamed camelCase on the wire — each
is a one-line code change and a document nobody updates. Within a few parts the
document is actively misleading, which is worse than absent, because a reader
trusts it.

Generating it from `app.openapi()` means the document is wrong only if the
application is wrong. The same argument applies to the event samples: they are
dumped from the event models, so a field added to `StepEvent` appears in the
documentation the next time it is generated, and a field removed disappears.

What cannot be generated is the prose — why tickets exist, why replay comes before
live, why a 404 rather than a 403 — and that is exactly the part worth writing by
hand.

**The traceability matrix says six requirements have no test. Is that not a failure?**

It is the document doing its job. A traceability matrix exists to find the gaps,
so one that reports none has either perfect coverage or a lazy author, and the
second is far more likely.

Of the six, three are honest consequences of decisions recorded elsewhere: the
payments service is a separate repository that does not exist yet, the mock
provider cannot evaluate prompt quality, and the same mock always declines vision
so nothing measures the model's judgement about a mark. Two are known limitations
with phase notes: shadow DOM and the WebSocket frame size. One is the live-provider
KPIs, which this part tried to measure and could not because the provider was down.

The distinction that matters is between a gap somebody chose and a gap nobody
noticed. All six are the first kind, and each says which decision produced it.

**What would you do differently, given the whole thing again?**

Three things.

The metric that measured recovery per attempt rather than per failed step was
wrong for two parts before I noticed, and reported 36% for a run that rescued 80%
of what broke. I would define the denominator with the metric, in the same commit,
because a metric measured the wrong way is worse than no metric: it is confidently
wrong and it looks like evidence.

I would run the thing end to end earlier. The first real demo, in B21, found six
bugs the suite had never caught — a date field filled with a city name, a cookie
banner defeating the entire ladder, an extract whose result never reached the
planner. Every one needed a real page and a real sequence, and none of them was
exotic.

And I would put the substring rules under test from the first one. Four times a
broad substring match on a security-adjacent check matched something it should
not: `token` in `input_tokens`, `pass` in `passengers`, `pay` in `Payment
history`. Each was caught later than it should have been, and the fourth was
caught by a test only because I had finally started writing tests aimed at that
specific failure shape.

## Follow-ups

- **`docs/traceability.md` and `docs/security.md` are maintained by hand**, and a
  renamed test makes either wrong with nothing failing. The extraction script used
  in this part is repeatable and is not wired into CI; a job running it would be
  about ten lines and would close the gap permanently.
- **`docs/api.md` is generated but not regenerated.** It is correct as of this
  tag, and a new endpoint will not update it. The generator should be a `make`
  target and ideally a CI check that the committed file matches a fresh one.
- **No live-provider KPI numbers.** The one attempt failed on the provider's
  availability. A later run when the model is healthy would replace the only
  section 9 figures currently measured entirely under a mock.
- **The diagrams are Mermaid in Markdown**, which GitHub renders and a PDF
  export will not. If the submission needs PDF, they need exporting to images.
