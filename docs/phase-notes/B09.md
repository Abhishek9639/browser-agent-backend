# B09 - Screenshots, storage, budgets

## What was built

Three small pieces the agent loop needs before it can run: a frame to show, somewhere to put it, and a reason to stop.

- `app/agent/browser/screenshots.py` - capture, downscale, compress, base64.
- `app/services/storage.py` - `ScreenshotStorage` protocol and a local implementation.
- `app/agent/budget.py` - `TaskBudget`.
- 71 unit tests.

## Key decisions

**PNG first, then one resize and one encode.** Playwright can emit JPEG directly, but we need to downscale as well, and encoding to JPEG at 2560 wide and then resizing compresses detail that is about to be thrown away, then compresses the artefacts again. Capturing lossless PNG and letting Pillow do both in one pass is both better looking and smaller.

**Image size and viewport size are stored separately.** They are usually different: a 2560-wide retina viewport becomes a 1280-wide frame. The `bbox` in the section 6.1 `step` event is in page coordinates, so the client needs both numbers to draw the highlight in the right place. Keeping only the image dimensions would make every highlight wrong on a high-DPI display.

**Compression runs in a worker thread.** Pillow is CPU-bound and takes a few milliseconds per frame. One frame per action across three concurrent tasks is enough to make the event loop stutter, and CLAUDE.md is explicit that nothing in the agent path blocks. The same applies to every filesystem call in the storage layer.

**A ref is validated, not sanitised.** This is the important one. `load()` matches against an anchored `<uuid>/<four digits>.jpg` pattern and refuses everything else. Stripping `..` from caller input is whack-a-mole: there is always another encoding, another separator, a null byte, a double-encoded slash. Refusing everything that is not exactly the expected shape has no such tail. Sixteen hostile refs are in the test suite, including URL-encoded traversal, backslashes, null bytes and `....//`.

The ref will arrive from an HTTP path parameter once `GET /tasks/{id}/steps/{stepId}/screenshot` exists, so it is treated as hostile input now rather than when that endpoint lands.

**A malformed ref and a missing screenshot return the same 404.** Different responses would tell an attacker their probe was at least well-formed, which is the first bit of information any traversal attempt wants.

**Refs are opaque and never absolute.** Callers store what `save()` returns and hand it back. They never join paths or see the filesystem, which is exactly what lets an S3 implementation drop in behind the same protocol with the ref becoming an object key.

**Budgets check time before steps.** A task that has exhausted both was really stopped by the clock; reporting `MAX_STEPS` would send someone to look at the wrong limit. The two exist because they fail differently: a redirect loop burns steps fast and is caught by `MAX_STEPS`, while a hung page burns none at all and would run forever without `MAX_TIME`.

**`check()` and `consume_step()` are separate.** Recovery retries within a step, and an approval pause, both call `check()` many times without a step having run. If checking spent the allowance, a task with one recovery-heavy step would report itself out of budget after a single action.

## Two things the work turned up

**A test that could not fail.** The first `test_nothing_escapes_the_root` fed malformed refs, which the pattern rejects before the containment check is ever reached, so the second layer of the guard was untested dead code as far as the suite knew. A symlink planted inside the tree is the only way a *well-formed* ref resolves outside it, so that is what the test now does. Removing the containment check makes it fail, which is the property a security test needs.

**I made the gate 40 seconds slower, then took it back.** The image fixture built noise with a per-pixel comprehension: at 2560x1600 that is four million Python tuples, several times over. `make check` went from 47s to 87s and `test-fast` was 37s for tests that touch no browser at all. One `Image.frombytes` call with `random.randbytes` does the same job; the gate is back at 66s and `test-fast` is 7s. Worth watching, because slow fixtures are easy to add and nobody attributes the slowdown to them.

## Viva questions

**Why 1280 wide and quality 60, rather than just sending the full screenshot?**

Because it is a live-view budget, not an aesthetic choice. Spec section 9 asks for a live update within one to two seconds of each action, and section 6.1 puts the frame inline in the WebSocket event as base64, which is a third larger again than the bytes. A full-resolution PNG of a retina viewport is megabytes; at one frame per action over a home connection that misses the target on network time alone before anything else goes wrong. At 1280 and quality 60 a typical page frame is tens of kilobytes. The measured saving is in the suite: `test_downscaling_saves_a_lot_of_bytes` asserts the scaled frame is under half the full-size one.

**Why is `ScreenshotStorage` a Protocol when there is only one implementation?**

Because the second one is already specified. Spec section 2 shows screenshot storage as "local FS to S3/MinIO", so the interface is the thing that will survive and `LocalFileStorage` is the thing that will not. Writing the callers against the protocol now means the migration touches one construction site instead of every call site. It also shapes the design in a way that pays off immediately: because a ref has to be meaningful to an object store as well as a filesystem, it is an opaque key rather than a path, and that is exactly the property that makes traversal impossible.

**How does the step budget interact with the recovery ladder?**

They are deliberately independent. `AGENT_MAX_STEPS` bounds how many *actions* a task takes; `AGENT_MAX_RETRIES_PER_STEP` bounds how many times one action is retried within the seven strategies of section 4.8. A step that needs four recovery attempts still consumes exactly one step, which is why `check()` does not spend the allowance and only `consume_step()` does. Without that separation a single stubborn element could burn a quarter of the task's twenty-five steps while making no progress, and the failure would be reported as "too many steps" when the real story is one element that could not be found.

## Follow-ups

- Nothing calls any of this yet. The orchestrator wires capture to the step loop, storage to the step row's `screenshot_ref`, and the budget to the `while` condition.
- `delete_task` exists but nothing calls it. It belongs on task deletion, and on a retention sweep if screenshots are ever kept beyond a run.
- `LocalFileStorage` writes under `STORAGE_DIR`, which is gitignored. There is no disk quota: a long run with many steps will accumulate frames until something prunes them.
- `AGENT_APPROVAL_TIMEOUT_SECONDS` keeps its `AGENT_` prefix rather than the bare `APPROVAL_TIMEOUT_SECONDS` the part listed, so it matches the other four budget settings it sits with.
