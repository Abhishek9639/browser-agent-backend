# B06 - Auth: JWT, JWKS, register, login

## What was built

The identity half of spec section 2: argon2 password storage, RS256 access tokens, a published JWKS so payments can verify without a shared secret, and the two endpoints that issue them.

- `scripts/gen_keys.py`, `app/core/jwt_keys.py`, `app/core/security.py`.
- `GET /.well-known/jwks.json` at the root, `POST /api/v1/auth/register`, `POST /api/v1/auth/login`.
- `get_current_user` bearer dependency.
- `docs/auth.md` with the sequence diagrams.
- 23 unit tests, 39 integration tests.

## Key decisions

**RS256, not HS256.** With a shared secret, payments would hold a key that mints backend tokens, so compromising the smaller service would compromise the larger one, and rotation would need both deployed together. With RS256 the private key never leaves this process, payments verifies from a public document it can cache, and rotation is: publish both keys, sign with the new one, retire the old after 15 minutes.

**`algorithms=["RS256"]` on decode is the single most important argument in this part.** It closes `alg: none` and the RS256-to-HS256 downgrade, where an attacker signs with HS256 using the public key as the HMAC secret. Both have tests. The downgrade test is built by hand with `hmac`, because PyJWT refuses to *encode* HS256 with a PEM, and an attacker is not using PyJWT: testing through the library's own guard rail would have proved nothing about our verifier.

**Login failures are opaque, registration is not.** A wrong password and an unknown email return the same status, code and message, and the unknown-email path still runs an argon2 verification against a throwaway hash so the timing does not differ either. Registration's duplicate-email 409 does confirm an address is registered, which is the trade the part specification asks for, and is the normal one: a register form that silently accepts a duplicate is unusable. The mitigation is rate limiting at the edge in B10, noted in `docs/auth.md`.

**A malformed email fails login with 401, not 400.** Validating the address shape at login would let someone distinguish "never a valid address" from "valid but wrong", which is a weaker version of the same oracle. Register validates strictly; login only normalises.

**`get_current_user` re-reads the user from the database.** The token alone would be enough to identify the caller, but then a deleted account would keep working until its token expired, and a demotion from `ADMIN` would take up to 15 minutes to apply. Reading the row costs one indexed lookup and makes both immediate. The role used for authorisation comes from the row, not the token claim.

**`create_access_token(user)` is a method, not a free function.** The part specification writes it as a function in `security.py`. It takes a keypair and settings, and threading both through every call site would be noise, so `TokenService` binds them once at construction and the call site reads as specified. `hash_password` and `verify_password` need no configuration and stayed as module functions.

**Email validation is a regex, not `EmailStr`.** Pydantic's `EmailStr` needs `email-validator`, which is not in the spec section 3 stack, and CLAUDE.md says to ask before adding one. The regex is deliberately permissive: anything stricter rejects addresses that are legal under RFC 5321, and the only real proof an address works is sending to it. Happy to switch if you want the dependency.

## The transaction exception

B05 established that services never commit. `LOGIN_FAILED` is the one sanctioned exception, and it is worth understanding rather than memorising.

A failed login raises `InvalidCredentials`, which propagates out of the request. `Database.session()` rolls back on an exception. So an audit row written through the request's session is discarded precisely when it matters most: the requests a security review cares about are exactly the ones that failed.

`AuthService._audit_failed_login` therefore opens its own session and commits it before the error propagates. `test_failed_login_audit_survives_the_rollback` proves it by reading the row through a *separate connection*: if it is visible there, it really was committed rather than merely staged.

This leaks state into the test database, which is the honest cost. An autouse fixture clears committed audit rows before each integration test, and it runs before rather than after so a failing test leaves its rows to inspect. Two B04 tests failed the first time this landed, which is how the contamination was found.

## Viva questions

**Walk through how the payments service validates a token it has never seen.**

It fetches `GET /.well-known/jwks.json` once and caches it for five minutes. A request arrives with `Authorization: Bearer eyJ...`. It reads the token header without verifying anything, takes the `kid`, and looks for a JWK with that id in the cached set. It builds a public key from the `n` and `e` values in that JWK, then verifies the signature with RS256 and checks `iss`, `aud` and `exp`. At no point does it hold a secret, call back to the backend per request, or need a database. That is why the `kid` is in the header: without it, a verifier facing two published keys during a rotation would have to try each one. `test_a_login_token_verifies_against_the_published_jwks` does exactly this over HTTP, touching no PEM.

**Why argon2 rather than bcrypt or SHA-256?**

A plain hash like SHA-256 is designed to be fast, which is the opposite of what password storage wants: an attacker with a dump wants to try billions of candidates, and speed is their advantage. bcrypt is deliberately slow but only CPU-hard, so it parallelises well on GPUs, and it silently truncates at 72 bytes. argon2id is memory-hard: each guess needs a configured amount of RAM, which is expensive to replicate across thousands of GPU cores. It is also the current OWASP recommendation, and it salts automatically, so the same password registered twice produces different digests. A test asserts that.

**Why include `jti` when nothing uses it?**

Because adding it later is not a change you can make retroactively. `jti` is a unique id per token, and it is what a revocation list, a replay check or an audit correlation would key on. If a stolen token needs revoking before its 15 minutes elapse, the mechanism is a deny-list of `jti` values, which only works if tokens already carry one. Adding it in a later part would mean every token issued before that deploy lacks the field, so the check would have to tolerate its absence, which is precisely the gap an attacker uses. It costs sixteen bytes.

## Follow-ups

- Refresh cookie, rotation, reuse detection, `POST /auth/refresh`, `POST /auth/logout` and `GET /auth/me` are B07. The `refresh_tokens` table and `RefreshTokenRepository` from B04 and B05 are waiting.
- Rate limiting on auth is B10, per spec section 10. Until then register and login are unthrottled, which is also what makes the 409 on register a usable enumeration channel.
- `jti` is recorded but never checked. A revocation list would go in `TokenService.decode_access_token`.
- `TokenService` is constructed per request from settings and keys. If key loading ever becomes expensive, it should move onto `app.state` like the database.
