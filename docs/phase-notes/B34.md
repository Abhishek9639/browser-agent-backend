# B34 - Tolerate a racing refresh

## What was built

A short grace window for refresh-token reuse, `REFRESH_REUSE_GRACE_SECONDS` (default 10). A just-rotated token presented again gets an access token and no new refresh cookie; the chain is not destroyed. The frontend was also made to share one refresh across callers.

## Key decisions

The audit log showed `TOKEN_REFRESHED` then `TOKEN_REUSE_DETECTED` one second apart: one client had raced itself, and the reuse policy treated it as theft and revoked every session. The real fix is on the client (one refresh in flight), but the server should not turn a client race into a full logout, so both were changed. Only a rotated token qualifies (it has a successor), within the window, with a live session left; logout-revoked and chain-killed tokens are never forgiven.

## Viva questions

**1. Why did two simultaneous refreshes log the user out?**
Rotation is single-use. The second request presented an already-revoked token, which is indistinguishable from a replayed stolen cookie, so the whole chain was revoked.

**2. Why return no new cookie in the grace case?**
The winning request already issued the successor. Issuing a second would fork the chain and leave two live tokens from one lineage.

**3. What does the window cost in security?**
A cookie replayed within seconds of rotation yields one short-lived access token. It cannot mint new refresh tokens, and anything later still triggers full revocation.
