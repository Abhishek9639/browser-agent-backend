# B17 - Task runner and task API

## What was built

The part that turns a submitted row into a running agent, and the endpoints a frontend talks to.

- `app/services/task_runner.py`: one runner per process, started and stopped by the lifespan. Owns Playwright and the Chromium it launches, the concurrency limit, and the cancel flags.
- `app/services/task_service.py`: every rule about what a task is, who may see it, what a duplicate is, when a cancel is allowed.
- `app/api/v1/tasks.py`, `app/schemas/task.py`: the seven spec section 6 endpoints, camelCase, documented for the generator.
- `CancelSignal` in `app/agent/contracts.py`, checked by the orchestrator at phase boundaries.
- 52 tests: 18 unit for the runner, 34 integration for the API and the runner against real rows.

## Key decisions

**The browser is shared, the context is not.** Launching Chromium costs about a second, which would dominate a short run if it were paid per task. A context is cheap and is the thing that actually isolates one task's cookies and storage from another's, so the runner launches one browser at startup and hands out a context per task.

**A queued task stays SUBMITTED because the orchestrator writes PLANNING as its first act.** There is no separate queue state to keep in sync: the semaphore holds the coroutine before the loop starts, so the row simply has not moved yet. The history screen shows exactly what is true.

**Cancellation is a flag, not `Task.cancel()`.** `asyncio.CancelledError` arriving at an arbitrary await would leave the run with no chance to settle its status or publish a final event, and catching it to do that work is exactly the anti-pattern the asyncio docs warn about. A flag read at known points stops the loop at a known point. Closing the context alongside it makes an action already in flight fail immediately instead of waiting out its timeout.

**The cancel endpoint writes the row, and the flag is only an optimisation.** Writing `CANCELLED` is what actually stops the task: the orchestrator refuses to move a task that is already terminal, so the cancel holds even if the signal never arrives, or arrives at a worker that is not running it. That also means cancelling a task this process does not hold is not an error.

**Startup finishes what the last process abandoned.** A task left `ACTING` by a crash has no worker and never will, because the coroutine that owned it died with the process. Leaving it alone shows a user a task that runs forever. Almost all of them become `EXECUTION_FAILED`; one left `AWAITING_APPROVAL` becomes `TIMED_OUT`, because nobody answered and decision A4 already calls an unanswered approval a timeout. It is also the only terminal state the lifecycle allows from there, which is the table agreeing rather than a coincidence.

**Duplicate detection only counts live tasks.** Asking for the same thing tomorrow is a new task; asking twice while the first is still running is almost always a double-submitted form. The existing task id goes in the 409 message because the client's next move is to open it.

**Ownership is checked on the task, and the step is then pinned to it.** Both halves matter. Without the first, anyone can read anyone's steps. Without the second, a valid step id from your own task reads a step belonging to someone else's.

**Screenshots are `private, no-store`.** A frame can show whatever the page showed, including somebody's account details, so no shared cache and no proxy gets to keep a copy.

## Three bugs the manual run found

The endpoints and the unit tests were all green before any of these showed up. Running the thing for real is what surfaced them.

**Background tasks are not "after the commit".** `POST /tasks` returned 201 with a task number, and the row then did not exist. Two faults in one: `TaskRunner.submit` is synchronous, so Starlette ran it in a worker thread where `asyncio.create_task` has no running loop; and the resulting exception propagated up through the exit stack that still owned the request transaction, rolling back the row the client had just been told about. FastAPI background tasks run *inside* that exit stack, so anything scheduled there can read a row that has not been written yet. The fix is an after-commit hook list on the session dependency, which is the thing that actually owns the transaction: callbacks registered there run once it has committed, and never if it did not.

**The loop threw away everything `extract` read.** The agent would extract the results list, learn nothing from it, and extract again until the step budget ran out. `StepSummary` had no field for it and the orchestrator never passed `ActionResult.extracted` on, so an action whose entire purpose is reading the page produced nothing the planner could act on. Extracted text now reaches the planner, capped so a page of it cannot crowd out the current page state. The mock has expected the `extracted:` label since B12; nothing had ever supplied it.

**`SUBMITTED` had no route to `EXECUTION_FAILED`.** A task whose browser will not launch, and a task left queued by a crash, both need to fail without ever planning, and the lifecycle refused the transition so they would have stayed live forever. Added to the table, with the reason written next to it.

There was also a fourth, caught by a test rather than the run: building the step detail response straight off the ORM row tried to lazy-load three `lazy="raise"` relationships. That guard earned its place.

## Viva questions

**Why not use FastAPI's `BackgroundTasks` to start the agent, given that is what it is for?**

Because it does not mean what it appears to mean. Background tasks run inside the exit stack that still holds the request's transaction, so a job scheduled there starts before the session commits and can look for a row nobody has written. I found this the direct way: the endpoint returned 201 with a task number and the task then did not exist, because the background job raised, the exception unwound through the exit stack, and the transaction rolled back after the client had already been told it succeeded.

The fix puts the hook where the transaction actually ends. The session dependency owns the `async with` that commits, so a callback list on it runs after the commit, and never at all if the request failed. That also reads as what it is at the call site: `after_commit.append(...)` rather than `background.add_task(...)`, which claims an ordering it does not have.

**A run can be cancelled from the API, by shutdown, or by the loop noticing a status written elsewhere. Why three mechanisms?**

They answer different questions, and only one of them is the real one. Writing `CANCELLED` to the row is what stops the task: the orchestrator refuses to move a task that is already terminal, so the cancel holds whatever else happens, including when the task is running on a worker that never hears about it.

The flag and the context close are latency. Without them a cancel is noticed at the next status write, which could be a thirty second navigation away, and the user watches a task they have cancelled carry on clicking. The flag is read between phases, and closing the context makes an action already in flight fail at once instead of waiting out its timeout. Shutdown is the third because a process going down has no time to be polite: it signals, waits briefly, and writes the terminal status itself for anything that did not settle in time, since a row left `ACTING` is exactly the state the next startup has to guess about.

**The runner holds queued tasks on a semaphore. Why is that not a queue?**

Because it has none of the properties that make a queue worth having. It does not survive a restart: the coroutines parked on that semaphore die with the process, which is why startup has to sweep up after them at all. Another worker cannot take the work, so a busy process cannot shed load to an idle one. There is no retry, no dead letter and no visibility into depth beyond a number in one process's memory.

What it does do is enforce the section 4.2 concurrency limit correctly within one process, which is what this deployment is. The honest framing is that the semaphore is the limit and the dictionary of asyncio tasks is bookkeeping, and the moment there is more than one worker both need to become a real queue and a shared cancel channel. That is the same boundary the in-memory event bus runs into, and for the same reason.

## Follow-ups

- Single process. More than one worker needs a real queue, and a cancel signal that crosses workers, at the same point the event bus needs Redis.
- Nothing publishes to the event bus outside the orchestrator yet; the WebSocket and the stream ticket are the next part.
- `POST /tasks` does not reserve credits. Spec section 7 wants `MAX_STEPS x 2` held at submission and settled on a terminal state.
- The runner launches Chromium at startup even if no task ever arrives. Fine for a demo, wasteful for a service that is mostly idle.
- `GET /tasks/{id}/recovery-attempts`, `/ground`, `/approve`, `/reject`, `/cache-match` and `/replay` are still to come.
