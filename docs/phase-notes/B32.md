# B32 - Drive the user's own browser

## What was built

An opt-in mode where the agent attaches to the user's running Chrome over CDP (`AGENT_CDP_URL`), opens its own tab there and brings it to the front. Also `AGENT_SLOW_MO_MS`, the focus step for any visible browser, and `scripts/chrome_debug.ps1`.

## Key decisions

The default is unchanged: with the setting empty every task still gets an isolated context. The new mode is an explicit exception recorded in spec section 4.13 and ADR-013. Teardown is the part that needed care: the driver must not close a context it does not own, or closing a task would close the user's windows.

## Viva questions

**1. Why is attaching to the user's browser opt-in rather than the default?**
It removes the per-task isolation the sandbox relies on. Cookies and storage become the user's, so it has to be a conscious choice, and the default keeps the guarantee.

**2. What stops the agent closing the user's windows?**
The driver tracks only the tabs it opened or that popped up, closes just those, and skips `context.close()` when it did not create the context.

**3. Why one concurrent task in this mode?**
Tasks would share one context, see each other's tabs and fight over which tab is in front.
