# B21 - Error recovery strategies

## What was built

The ladder from spec section 4.8, and the first end-to-end runs that prove the whole thing works. The demo is written up separately in [B21-first-e2e.md](B21-first-e2e.md); this note is about the code.

- `app/agent/recovery/strategies.py` and `runner.py`, seven ordered strategies behind one `Recovery` collaborator.
- `GET /api/v1/tasks/{id}/recovery-attempts`.
- 25 tests, plus three fixture pages that each break in one specific way.

## Key decisions

**A strategy never grades its own attempt.** Every rung does the same three things: work out a better locator, run the original action against it, and hand the result to the verifier. A strategy that decided for itself whether it had worked would report success whenever Playwright did not raise, which is most of the time and almost never the question.

**`applicable` means "could this help", not "could this run".** This is the difference between the ladder working and not. A cookie banner makes rungs one to four runnable and useless: the locator was never the problem, the thing on top of it was. They now stand down while the target is covered, so the retry budget reaches the rung that closes it. The first chaos run failed precisely because they did not.

**Skipped rungs do not spend the budget, but they are still numbered.** A rung that could not apply has not cost a retry, so the budget is for attempts that actually touched the page. Every attempt is still recorded and numbered sequentially, because `attempt_number` is the ordering key on the row and two rows sharing one makes a step's history unorderable.

**The overlay rung closes everything it recognises.** The chaos combination puts a cookie banner and a newsletter popup on the same page, and clearing one still leaves the click blocked. Capped at three, because a page that keeps producing modals is a page to give up on rather than to fight.

**Closing a banner must not consent to anything.** The close-button labels are ranked, and "Reject non-essential" outranks "Accept all cookies". The agent is clicking this to get on with its task, not because the user decided anything, so the least consenting reading of the overlay wins. Matching is on the whole label rather than a substring, so "Accept" does not also match "Accept and book this flight", which is a button that spends money.

**The verification baseline is the page immediately before the retry.** Not the page that failed. A rung that changes the page itself, such as one that closes a modal, would otherwise satisfy `dom_changed` on its own cleanup and report a click that never landed as a success. That bug was live for one demo run and the symptom was a step that passed while the browser had not moved.

**Recovery returns the state it ended on.** The loop carries a page state between steps, and after a successful rescue that state has to be where the retry left the browser. Returning the state that failed had the agent navigate to the results page and then plan its next move against the search form it had already left.

**Recovery events are published live, ahead of their rows.** This is the opposite of the rule for step events and it is deliberate. A step event is history, and spec section 6.1 promises a reconnecting client can be caught up from the database, which only holds if the database is never behind the stream. An attempt is commentary on a step that does not exist yet: the step row is written once, after verification, with its attempts alongside it in the same transaction, so there is no row to lead with. Buffering the attempts until then would show a user nothing during the slowest part of a run, and a ladder can take thirty seconds. The events therefore go out as they happen and the durable record is `recovery_attempts`, served by its own endpoint. A client that reconnects mid-ladder loses the commentary and keeps the history, which is the right way round: the history is what it cannot reconstruct.

**A visual grounding rung exists and is deliberately never applicable.** A placeholder that returned success would end the ladder before the rungs below it ran.

## The failure sentence

Spelled out because it is the only part of this a user ever sees:

```text
Step 5: Could not click 'Search flights': tried scrolling to it and closing a popup.
```

"Step 5 failed" tells someone nothing they can act on. This tells them the button was found, reached for twice, and still would not take a click, which is enough to guess that the page is not what the agent thought it was.

## What the demo cost in wall-clock time

The clean run takes five seconds and the chaos run takes forty-nine. Almost all of the difference is two failed `scroll_and_wait` attempts at ten seconds each, because a failed action waits out the browser's action timeout before the next rung gets its turn. The ladder spends its budget in strategy order rather than in order of what the failure looked like, and picking the rung from the error code is the obvious next improvement.

## Viva questions

**The strategies are ordered, but `applicable` lets later ones run first. Is the order still meaningful?**

The order still decides who goes first among the rungs that could plausibly help; what `applicable` removes is the ones that cannot. Those are different questions and conflating them is what broke the first chaos run: three rungs that re-locate an element ran against a target with a modal on top of it, each failed for the same reason, and the budget was gone before the rung that closes modals was reached.

The alternative is a bigger retry budget, which costs ten seconds per useless attempt and does not stop them being useless. The version I would build next goes further in the same direction and picks the rung from the failure: an element-not-found error means re-locate, a timeout on a visible element means something is covering it or it is off screen.

**Why is the verifier the judge of a recovery attempt rather than the strategy that made it?**

Because the strategy knows whether its locator resolved, which is not the same as whether the step worked. Playwright clicking something successfully tells you a click happened, not that it hit the right thing or that the page did what the plan expected. A strategy that reported its own success would turn "I found an element and clicked it" into "the step is done", and on a page with a modal over it that element is often the modal's own button.

Using the verifier also means recovery inherits every check and every default from the deterministic verification part, including the ones that catch a click that changed nothing. The cost is a perception and a verification per attempt, which is small next to the ten seconds a failed action already spends.

**Recovery events are published before their rows are written, which is the opposite of the rule for steps. Why?**

Because they are different kinds of thing. A step event is history: spec section 6.1 lets a client reconnect and be caught up from the database, which only works if the database is never behind the stream. An attempt is commentary on a step that does not exist yet, since the step row is written once, after verification, with the attempts alongside it in the same transaction.

The alternative was to buffer the attempts and announce them after the step, which would have shown a user nothing at all during the slowest part of a run. A ladder can take thirty seconds. So the events go out live and the durable record is `recovery_attempts`, served by its own endpoint; a reconnecting client loses the commentary and keeps the history. The asymmetry is deliberate rather than an oversight, and it was reviewed and kept on exactly this reasoning: the two event kinds carry different promises, so they get different ordering rules.

## Follow-ups

- Pick the rung from the failure's error code rather than walking the ladder in order. That is the ten seconds per failed attempt.
- Recovery attempts are not part of the WebSocket replay. A client that reconnects mid-ladder sees the step's outcome but not what was tried, and has to fetch the endpoint.
- `VisualGrounding` is a placeholder until the grounding part lands.
- The overlay label list is English only.
- A rung that partly works, such as closing one of two overlays, is recorded as a plain failure. The step log would read better if it said what it did before it failed.
