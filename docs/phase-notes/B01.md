# B01 - Repo scaffolding

## What was built

An empty but fully governed Python 3.12 project. No application code: the point of this part is that every later part lands into a repo where the rules, the layout, and the quality gate already exist.

- `CLAUDE.md`, the permanent rules: spec is source of truth, async everywhere, strict typing, the `browser-use` ban, the architecture direction, the secret and logging bans, and the one-part-at-a-time pace.
- uv application project pinned to Python 3.12 via `.python-version`, dev dependencies only (ruff, mypy, pytest, pytest-asyncio, pytest-cov, pre-commit). No runtime dependency is installed yet because nothing imports one.
- Tooling in `pyproject.toml`: ruff line length 100 with a security and async aware rule set, mypy strict over `app/`, pytest `asyncio_mode=auto`, coverage scoped to `app`.
- The package tree under `app/`, with `app/agent/` split into its nine subsystems.
- `Makefile` with the twelve required targets, and `make check` as the gate.
- `.gitignore`, `.editorconfig`, `.env.example`, `.pre-commit-config.yaml` (ruff, ruff-format, end-of-file, trailing whitespace, gitleaks).
- `README.md`, `docs/CHANGELOG.md`, and three smoke tests.

## Key decisions

**The package root is `app/`.** Decision A1 in the plan. The spec's section 4.1 paths are relative to it, so `agent/browser/driver.py` on paper is `app/agent/browser/driver.py` on disk. `alembic/`, `tests/` and `demo_sites/` stay at the repo root: the first two are not application modules, and the demo sites are a separate ASGI app on port 8200 that must never be mounted into the API.

**`app/models/` and `app/repositories/` are top level, not under `app/db/`.** The B01 prompt specifies them as siblings of `db/`; `docs/BACKEND_PLAN.md` had drawn them nested. The prompt wins under the rule that a part prompt is authoritative, so the plan's tree now disagrees with the repo and needs a one-line correction.

**Targets that depend on later parts fail with a message, not a stack trace.** `dev`, `migrate`, `db-up` and `db-down` check for the file they need and explain which part delivers it. A Makefile that exists but lies about what it can do is worse than one that says "not yet".

**No runtime dependencies yet.** FastAPI, SQLAlchemy and the rest arrive in the part that first imports them, so the lockfile always reflects what the code actually uses.

**Coverage does not omit `__init__.py`.** The conventional omit made `make test` warn that no data was collected, because at this point every file in `app/` is an `__init__.py`. Including them costs nothing and keeps the output honest.

## Viva questions

**Why is `app/agent/` forbidden from importing FastAPI?**

The agent core is the part with real logic: the perceive, plan, act, verify, recover loop. If it imports FastAPI, testing one decision needs an HTTP stack, a request, and a running app. Keeping the dependency pointing one way (services drive the agent, never the reverse) means the loop can be tested with a mock LLM and a fake page state, which is exactly what spec section 11 asks for. It also keeps the option of running the agent from a CLI or a worker later without dragging the web framework along.

**What does `asyncio_mode=auto` do, and why set it?**

pytest-asyncio normally requires every async test to carry an `@pytest.mark.asyncio` decorator; without it the coroutine is never awaited and the test silently passes. `auto` makes pytest-asyncio collect any `async def` test automatically. Since the spec mandates async I/O throughout, nearly every test here will be async, so the decorator would be noise on hundreds of tests and a silent false pass whenever someone forgets it. `tests/unit/test_smoke.py::test_asyncio_mode_is_auto` is an undecorated async test that only runs if the setting is active, so the config is self-verifying.

**Why is `make check` lint plus typecheck plus unit tests, rather than the full suite?**

`check` is the per-part gate, so it has to be fast and must not depend on anything external. Integration tests need Postgres, chaos tests need the demo sites on :8200, and eval tests need either a mock provider or real LLM quota. Making the gate depend on a running database would mean either a slow feedback loop or a gate people skip. The full suite still exists as `make test`, and CI runs the heavier tiers where the services are available.
