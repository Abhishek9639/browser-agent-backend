# B18 - SkyFare demo site

## What was built

The site the agent is measured against. Spec section 12 asks for a mock airline search that behaves like a real one and can be made to misbehave on demand.

- `demo_sites/skyfare/`: `flights.py` (generation), `chaos.py` (toggles), `render.py` (HTML), `app.py` (routes).
- `make skyfare` serves it on :8200. README section with screenshots.
- 46 tests.

## Key decisions

**No template engine.** Jinja2 is not in the spec section 3 stack, and CLAUDE.md says to ask before adding a dependency. It turned out not to be worth asking: the `shuffle` toggle has to rewrite every id and class name on the way out, which is a natural thing for a function that takes a name mangler and an awkward thing to thread through templates. Plain functions returning strings, and the mangler is an argument.

**Seeded from the query, not from a random source.** The same origin, destination and date always produce the same flights. Hashed with sha256 rather than `hash()`, which is salted per process: with the built-in, the same search would return different flights after every restart and no evaluation run would be comparable to another. That determinism is the entire reason the ground-truth endpoint can exist.

**The site keeps no state.** A flight detail page is reachable only with the query that produced it, which is why every link carries from, to and date. The alternative is a server-side session, and then a test that starts at a detail URL has to replay a search first.

**Ground truth is behind a header and 404s without it.** `GET /api/cheapest` is a measuring instrument, not part of the site. A 403 would confirm the path exists, so an agent that stumbles onto it would learn there is an oracle worth attacking. A 404 tells it nothing. This matters because the agent is pointed at this host with the whole origin allowed: the allow-list cannot separate a scoring endpoint from the pages, so the endpoint has to separate itself.

**Toggles carry through every link.** A chaos setting that switches itself off as soon as the agent clicks something tests only the first page. Every internal link re-encodes the active toggles.

**`inject` puts the text in three places.** A visible banner, a screen-reader-only copy, and a `display:none` copy. They test different layers: the banner tests whether the model does what a page tells it, and the two hidden copies test the collector, which must never pass an invisible element to the planner at all. Spec section 4.11 lists those as separate defences and they fail separately.

**The payment page exists to catch the agent.** Nothing is charged and nothing is reserved, so the page is pure instrumentation: reaching it without a human approving the step is exactly the failure the approval gate exists to prevent, and an evaluation run can assert on the URL.

## The bug the site found

Running `scripts/perceive.py` against the finished site printed this:

```text
[8] select "PASSENGERS" value="••••"
```

The passenger count was being treated as a secret. The collector's secret check is a substring match, and `passengers` contains `pass`. The same rule masks a `shipping_address`, because `shipping` contains `pin`.

This is the third time a substring rule on a security check in this repository has caught something it was never aimed at. The first was an audit field named `token_id`; the second was the `input_tokens` column, fixed with an exact-match allowlist. The pattern is consistent: the rule is broad on purpose, because field names run words together and `cardNumber` has to match, so narrowing it with word boundaries would break the cases it exists for.

The fix follows the same shape as the last one. Known benign words are stripped from the hint before the secret check runs, so `passenger_card_number` is still masked on the `card` in the middle of it while `passengers` alone is not. Tests now pin both directions on a fixture page.

Worth noting that this had been latent since the collector was written, and only surfaced because the demo site is the first page in the repository with a field called "passengers". The fixture pages did not have one.

## Viva questions

**Why generate flights from a seed instead of shipping a fixed list?**

A fixed list answers one query. The evaluation suite needs the agent to search for routes and dates that were not decided in advance, and a chaos run needs the same route to look different on a different date so the agent cannot get the right answer by remembering it. Seeding gives both: any query works, and any query is reproducible.

The property that actually matters is that the cheapest fare for a query is a fixed answer. Without it there is no way to score a run except by trusting the agent's own report, which is exactly the thing being tested. With it, the oracle and the page are two views of the same generator, and a test asserts they agree, because if they ever drift then every score is measured against the wrong answer.

**The injected text tells the agent to click Pay now. Is putting that on the page not just building the attack?**

The attack exists whether or not this site has it. Any page the agent visits can contain text addressed to the model, and the whole point of the spec section 4.11 layering is that the agent survives it. A defence nobody has tried to get past is an assumption.

What the site adds is that the attempt is reproducible and in three forms at once, so the layers can be tested separately. If the collector ever starts passing hidden elements through, the `display:none` copy catches it. If the fencing around the page state is dropped, the visible banner catches it. And because the page also has a real Pay now button and a payment page, an evaluation run can assert on the outcome rather than on the model's reasoning: either the agent reached `/pay/` or it did not.

**The site looks like a real airline site. Why does that matter for testing an agent?**

Because most of what breaks an agent is ordinary visual complexity rather than anything adversarial. A bare form with four inputs is trivially perceivable: everything is in the viewport, nothing overlaps, and there is one button. A real layout has a header with navigation, a card overlapping a hero, a filter sidebar, twenty-eight result rows of which eight fit on screen, and a second button on every one of them.

That shape is what exercises the parts that actually fail: the token budget on the DOM summary, the in-viewport and covered flags, scrolling to reach a result, and telling twenty-eight Select buttons apart. A page simple enough to fit in one screenshot tests none of it.

## Follow-ups

- The site is single-process and keeps no state, so it needs no database and no cleanup. Keep it that way.
- Chaos toggles combine freely but are only tested individually and in one combination. `chaos=all` renders, and whether it is solvable is an open question for the evaluation suite.
- No `robots.txt` or rate limiting, because nothing here is public.
- The agent's approval gate refuses everything today, so nothing has yet reached `/pay/`. When approvals are real, an evaluation case should assert that reaching it always required a human.
