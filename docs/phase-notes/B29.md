# B29 - Billing client with outbox

## What was built

The integration side of spec section 7. The payments service is a separate repository and nothing here implements it; what is here is the four calls, the arithmetic, and the mechanism that stops a call being lost.

- `app/services/billing_client.py`: the HTTP client, with retries only where retrying can help.
- `app/models/billing.py` and `app/repositories/billing.py`: the `billing_outbox` table.
- `app/services/billing.py`: `BillingService`, which decides what is synchronous and what is queued, and `OutboxWorker`, which delivers the queue.
- `app/domain/credits.py`: what a run costs, in the one place three callers can share.
- Wiring: register queues a grant, `POST /tasks` reserves synchronously, a terminal state queues a settle or a release.
- `docs/billing-integration.md`: the contract, written so the payments repository can implement against it.
- 48 tests.

## The one asymmetry that matters

Three of the four calls go through the outbox and one does not.

`reserve` is synchronous because a user submitting a task has to be told now whether they can afford it. A 402 has to arrive as a 402, with both numbers in it, on the response to the request they just made. Queueing that would mean accepting the task and refusing it later, which is worse than refusing it now.

Everything else is money owed in one direction or the other. A grant that is lost because payments was restarting is credits somebody paid for and never received; a settle that is lost is work somebody used and was never charged for. Neither can be fixed by retrying in the request, because the request is over. So the call is written to a table **in the same transaction as the business change it belongs to**: the user row and its grant commit together or neither does, and the terminal status and its settle commit together or neither does. A worker delivers what is there afterwards.

That is the whole design, and it is why the outbox is a table rather than an in-memory queue: a process that dies holding a queue loses it, and a process that dies holding a transaction loses nothing.

## Key decisions

**One pricer, in the domain layer.** Three places need the same answer: the orchestrator reports it on the run, the stats endpoint totals it over history, and the outbox settles it. A settle that disagrees with what the agent reported is the one bug here that costs somebody money, so the arithmetic is in `app/domain/credits.py` and the two copies that existed before this part are gone.

**Rounded up once, per task.** "Replayed steps 0.5, round up" has two readings and only one of them is a discount: rounding each half up separately charges a full credit for every replayed step. Three replayed steps cost two credits.

**A run that used nothing is released, not settled at zero.** Both leave the wallet in the same place. The ledger on the other side keeps "this task cost nothing" and "this task was measured at nothing" apart, and a release is the honest one for a task that never took a step.

**A 402 is never retried.** It is an answer. Retrying it reaches the same answer while the user waits, and the retry budget belongs to failures that might go away.

**A timeout is retried, which is what the idempotency keys are for.** A timeout means the answer was lost, not that nothing happened, so the retry has to be provably the same request. Every key is derived rather than random: `signup:<userId>`, `reserve:<taskId>`, `settle:<reservationId>`, `release:<reservationId>`.

**The keys live next to the table, not next to the client.** `app/models/billing.py`, because the agent loop writes an outbox row directly and must not import a service to do it. That also keeps the unique constraint and the function that populates it in one file.

**The outbox enqueue is `ON CONFLICT DO NOTHING`, not read-then-write.** Two workers settling the same reservation would otherwise race into a unique violation, and the transaction the loser takes down is the one writing the task's terminal status. Returning `None` for "already queued" is a success from the caller's point of view.

**`FOR UPDATE SKIP LOCKED` on the claim.** Without `SKIP LOCKED` a second worker blocks on the first one's row and the pair runs at the speed of one.

**A row that exhausts its attempts is left undone, not marked failed.** It is the evidence that somebody's credits are unaccounted for. Deleting it, or flagging it as finished, would hide exactly the thing a person needs to find.

**`BILLING_ENABLED` is checked in one place.** `BillingService` returns `None` from every method when billing is off, so every caller's happy path is identical in both modes. A branch at each call site would be four chances to forget one.

**`tasks.credits_used` is written whether or not billing is enabled.** It is the section 9 cost-per-task figure as well as the amount a settle charges, and a deployment that turns billing on later still wants the history. Only the call to payments is conditional.

## A window I could not close

The reservation is taken before the task row is committed, so a rollback in between leaves a hold with nothing attached to it. Only the payments expiry job clears that, which is what spec section 7 says the job is for.

I considered reserving after the commit instead. It is worse: the client would be told the task was accepted and then charged for it separately, or not at all, and a task that started before its payment was known is the thing the reservation exists to prevent. The window is small, it is recoverable by a job the spec already requires, and it fails in the direction of holding credits rather than spending them.

## Viva questions

**Payments is down for an hour. What breaks, and what does not?**

Task submission breaks: a reserve that cannot be answered is a 503, and no task runs unpaid. That is deliberate, and it is the only user-visible breakage.

Registration does not break. The grant is queued in the transaction that creates the account, so the user signs up, logs in and sees an empty wallet, and the credits arrive when payments returns.

Tasks already running do not break. They finish, write their terminal status, and queue their settle in the same transaction. Nothing waits on payments and nothing is lost.

When payments comes back the worker drains the backlog, with the same idempotency keys it would have used an hour earlier, so a call that had actually landed before the timeout is not applied twice.

**Why is the outbox row written in the business transaction rather than after it?**

Because "after it" has a gap, and the gap is where money goes missing. If the task's terminal status commits and then the process dies before the outbox row is written, the task is finished and nobody will ever charge for it: the run is over, there is nothing left to retry, and no job can tell the difference between a task that was settled and a task whose settle was never queued.

Writing both in one transaction makes that state unrepresentable. A finished task always has its charge queued, and a queued charge always belongs to a finished task. The cost is that the outbox lives in this service's database rather than in a queue, which is the right trade: the guarantee is worth more than the tidiness.

**What stops a settle being applied twice?**

Three things in a row. The unique constraint on `idempotency_key` means a second settle for the same reservation cannot even be queued. The worker marks a row delivered inside the transaction that claimed it, so a crash after the call and before the mark leaves the row claimable again but with the same key. And the key means the payments side recognises the repeat and returns the original outcome rather than applying it.

The third one is the only real defence, because it is the only one that survives this service being restarted mid-call. The first two make it rare; the contract makes it safe.

## Follow-ups

- **The outbox worker is per process.** Several share the backlog safely, but nothing outside a running process delivers it: a deployment with no API process up does not settle anything until one starts.
- **Nothing reconciles.** If a settle is delivered and the payments side records something different, nothing here notices. The evidence exists on both sides and comparing them is work nobody has done.
- **No metric for the backlog.** `pending_count` exists on the repository and nothing publishes it. An outbox depth gauge is the obvious thing to add next to the B27 metrics, and an alert on it would catch payments being down for longer than anybody noticed.
- **`pending_count` counts by fetching.** Fine at this size, wrong at any other; it wants a `SELECT count(*)`.
- **The expiry job is the other repository's.** This side depends on it and cannot test it, which is recorded in the contract document under what this side expects of the other.
