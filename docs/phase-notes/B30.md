# B30 - Docker images and GitHub Actions

## What was built

- `Dockerfile`: multi-stage, two targets, on the official Playwright Python image pinned to our Playwright version.
- `docker/entrypoint.sh`: migrations and a signing key before uvicorn.
- `.dockerignore`, `docker-compose.yml`, and `make up` / `down` / `logs` / `build`.
- `deploy/docker-compose.full.yml` and `.env.full.example` for the three-repository stack.
- `.github/workflows/ci.yml`: seven jobs, one required check.
- `docs/cicd.md`: what runs, how to verify a change to it, and the branch protection settings to apply by hand.

## Two bugs the first run found

**`LLM_PROVIDER` came from my `.env`, and the key did not.** Compose loads the repository's `.env` by itself, so the container inherited `LLM_PROVIDER=gemini` from my machine while the compose file passed the key as `GEMINI_API_KEY`. The settings field is `GOOGLE_API_KEY`, so the container started happily and failed the first task with `MissingApiKeyError`. Fixed by passing the names `app/core/config.py` actually reads.

The inheritance itself I kept. A developer with a provider configured in `.env` probably wants that provider in the container, and `LLM_PROVIDER=mock make up` overrides it for one run. It is documented, because "the stack behaves differently on your machine than in CI" is worth saying out loud.

**The first real run hit my own Gemini rate limit**, five verified steps in. Not a defect: the run had reached SkyFare, filled the form, searched and sorted before the provider refused, which is exactly the evidence the container was working. I re-ran it on the mock to finish the check without spending more quota.

## Key decisions

**The base image is pinned to the Playwright version, and CI's browser cache is keyed on the resolved version.** These are the same decision twice. The Python package and the browser build it drives ship together, and a mismatch fails at the first `page.goto` with a protocol error rather than at build time. Pinning the tag stops the image drifting; keying the cache on the resolved version stops CI pairing a new package with last week's browser. When `playwright` moves in `pyproject.toml`, the `FROM` tag has to move with it, which is a thing a person must remember and no test will catch.

**Dependencies are their own stage.** Application code changes on every commit and dependencies on the rare one. A single stage would rebuild `uv sync` on every push, and that is minutes each time.

**Non-root, using the base image's `pwuser`.** Two reasons and the second is the one that bites: a browser running as root is a sandbox with the door open, and every screenshot written to a mounted volume would be root-owned on the host.

**Migrations run in the entrypoint, not in a separate job.** Alembic serialises on the `alembic_version` row, so several replicas starting at once is safe, and a container that cannot migrate should fail rather than serve. `RUN_MIGRATIONS=0` exists for a deployment that would rather run them itself.

**The signing key is generated onto the volume when the volume is empty, never over an existing one.** A key regenerated on every restart invalidates every token already issued; a key baked into the image is a key in a registry. `JWT_GENERATE_KEYS=0` makes a missing key fatal instead, for a deployment that mounts real ones.

**The health check calls the endpoint the frontend and compose already use**, with a 40-second start period that covers migrations and the Chromium launch. Without it the container is reported unhealthy for the first few seconds of every start, and `depends_on: service_healthy` then waits for a condition that has already been met and reported wrongly.

**`gate` is the only required check.** Branch protection names jobs by name, so every job added later would mean editing the protection rule, and one somebody forgot would be silently optional. The gate also checks the results explicitly rather than relying on `needs`, because a job that only lists dependencies does not fail when one is skipped or cancelled, and cancelled is what a timeout looks like.

**The `image` job builds with compose rather than buildx and a registry cache.** Slower, and the point: it runs the same command `make up` runs, so it cannot pass against an image assembled differently from the one a developer gets. It also starts the stack, because a build proves the layers assemble and starting it proves the entrypoint runs.

**CI runs on the mock provider.** No secret, no quota, nothing another repository's rate limit can break. A regression gate should measure our code; the model's judgement is measured by the benchmark, by hand, with a key.

**The frontend and payments services are declared in the full stack and commentable in one block each.** Both repositories are still to be written. Declaring them with the environment they will need, and a comment saying to comment them out, is less work later than reconstructing them from the spec, and I checked that removing both leaves a valid file.

## Viva questions

**Why base the image on the Playwright image rather than `python:3.12-slim`?**

Because Chromium's system dependencies are about forty packages and the list changes between browser versions. Microsoft maintains that list for exactly the browser build the matching Python package drives, and getting it wrong produces a container that builds, starts, serves health checks, and then fails the first time a task tries to open a page — the worst possible failure shape, because it looks like an agent bug.

The cost is size: the image is around 2 GB against maybe 400 MB for a slim base plus what the agent needs. For a service whose entire purpose is driving a browser, that is the right trade. If it ever matters, the direction is a slim runtime with the browser mounted from a shared volume, not a hand-maintained package list.

**The entrypoint runs migrations. What happens when three replicas start at once?**

They serialise. Alembic takes a lock on the `alembic_version` row inside a transaction, so the first replica applies the migration and the others wait and then find nothing to do. All three then start serving against the same schema.

What this does not handle is a migration that is not backwards compatible with the code already running, which is a deployment ordering problem rather than a container one: dropping a column the old version still selects breaks it regardless of who runs the migration. The answer there is two deploys, expand then contract, and nothing in this part enforces it.

**CI passes and a developer's machine fails. What is the most likely reason?**

The `.env` file, which CI does not have and every developer does. Compose loads it automatically, so `make up` on a developer's machine inherits their provider, their ports and their credentials, while CI runs with the defaults in the compose file. That is exactly how the `GOOGLE_API_KEY` bug in this part surfaced: it could not have happened in CI, because CI has no `.env` to inherit.

Second most likely is the platform: the runner is `linux/amd64` and a developer on Apple silicon builds `arm64`, so anything depending on a prebuilt binary can differ. The Playwright base image publishes both, so this has not bitten yet.

## Follow-ups

- **No deployment.** CI builds images and throws them away: there is no registry and nowhere to deploy to. Pushing is a `docker/login-action` and two lines when there is somewhere to push.
- **Coverage is uploaded, not enforced.** No minimum, so nothing fails when it drops.
- **The `image` job rebuilds from scratch every run**, around six minutes, most of it pulling the base image. Deliberate, and the first thing to revisit if CI time becomes the complaint.
- **`make up` and `make db-up` use different compose files and different Postgres volumes.** Running both gives two databases and one of them is not the one the suite uses. The names make it visible rather than confusing, and a single file with profiles would be tidier.
- **The Playwright pin has to be moved by hand** in `Dockerfile` when `pyproject.toml` moves. Nothing checks that they agree; a CI step comparing the two would be cheap and is not written.
- **The chaos suite cannot run twice at once**, and `concurrency` only covers superseded runs on the same branch.
