# B04 - Data model and initial migration

## What was built

All nine tables from spec section 5, plus `refresh_tokens`, as SQLAlchemy 2 models grouped by aggregate, with eight native Postgres enum types and a hand-corrected migration that round-trips.

- `app/domain/enums.py` - eight enums, values matching the spec's own spelling.
- `app/models/` - `user.py`, `task.py`, `approval.py`, `audit.py`, `cache.py`.
- `migrations/versions/a78013bebd3a_*.py` - the schema.
- `docs/database.md` - ER diagram and per-table notes.
- 99 unit tests, 32 integration tests.

## Key decisions

**Enums store the value, not the member name.** SQLAlchemy defaults to persisting `member.name`, which would put `NAVIGATE` in the database while the API and the LLM schema both say `navigate`. `enum_column()` sets `values_callable` so one spelling runs end to end, and `test_enum_values_are_stored_not_member_names` asserts it against real Postgres. This also means section 4.4's allow-list is enforced by the database, not only by application code: `test_postgres_rejects_a_value_outside_the_allow_list` inserts `sudo_rm_rf` with raw SQL and it is refused.

**`task_number` comes from a sequence.** Spec section 5 shows `T-000123`. The obvious `SELECT MAX(task_number) + 1` loses a race under concurrent inserts, and `MAX` on a zero-padded string is the wrong comparison anyway. A sequence is atomic and the server default formats it in one expression: `'T-' || lpad(nextval('task_number_seq')::text, 6, '0')`. The sequence is bound to the metadata so `create_all` manages it too, which is what the test fixtures use instead of running migrations.

**`credits_reservation_id` is deliberately not a foreign key.** Reservations live in the payments service's own database (spec section 7), so a constraint here is impossible and pretending otherwise would be misleading. It is an opaque UUID, and a test asserts it has no foreign keys so nobody "fixes" it later.

**Everything is `lazy="raise"`.** In async SQLAlchemy an implicit lazy load either fails confusingly at await time or silently turns a list render into an N+1. Raising immediately makes the mistake obvious at the call site, and forces loading to be explicit with `selectinload`. A unit test walks every relationship on every model and asserts it.

**The task tree cascades; users do not.** Deleting a task removes its steps, decisions, verifications, recovery attempts, approvals and audit events, expressed as `ON DELETE CASCADE` in the database rather than left to the ORM, so a raw `DELETE` behaves the same way. Users are `RESTRICT`: deleting someone who owns tasks would silently destroy history. `cached_flows` is `SET NULL`, so invalidating a cache entry does not delete the tasks that used it.

Audit events cascade with their task. That is a real trade-off: it keeps the schema simple and tasks are not expected to be deleted in normal operation, but if audit retention becomes a requirement the fix is `task_id` nullable with `SET NULL`.

**`strategy_used` is text, not an enum.** The seven-rung ladder in section 4.8 is expected to grow, and adding a rung should not require a migration. Everything else with a fixed, spec-defined value set is an enum.

## What autogenerate got wrong

Worth recording, because the instinct is to trust the generated file:

1. **No `CREATE SEQUENCE`.** Alembic does not autogenerate sequences, so the `tasks` server default referenced a `nextval` on something that did not exist. Upgrade failed outright.
2. **Duplicate `CREATE TYPE`.** `risk_level` is used by both `approvals.risk_flag` and `llm_decisions.risk_level`. Autogenerate inlined the type in each `create_table`, so the second aborted with "type already exists". Types are now created once up front with `checkfirst`, and referenced with `create_type=False`.
3. **`drop_table` leaves enum types behind.** Downgrade appeared to succeed while leaving all eight types in place, so the next upgrade failed. This is the failure the round-trip test exists to catch.
4. **`credits_reservation_id` came out as generic `sa.Uuid`** rather than the Postgres `UUID` every other id uses. Fixed in the model.

The migration's docstring lists all four, so the next person reading it knows the file was edited and why.

## Viva questions

**Why enforce the action allow-list in the database when the code already validates it?**

Defence in depth against a class of bug the application cannot see. The planner output is validated by Pydantic, but rows also arrive from migrations, from a repair script, from a future bulk import, or from a bug that bypasses the service layer. A native enum means Postgres itself refuses anything outside the twelve actions, so the invariant holds regardless of which code path wrote the row. It also documents the allow-list in the schema, where anyone reading the database can see it. The cost is that adding an action needs a migration, which is the right amount of friction for a security-relevant list.

**What does `lazy="raise"` actually prevent, and what does it cost?**

In synchronous SQLAlchemy, touching an unloaded relationship silently emits a query; do that in a loop over 25 steps and you have 25 round trips instead of one. In async SQLAlchemy it is worse: the lazy load happens outside an await, so it raises `MissingGreenlet`, an error that points at the attribute access rather than at the query that should have eager-loaded. `lazy="raise"` converts both into an immediate, honest `InvalidRequestError` naming the relationship. The cost is that every query site must say what it needs, with `selectinload(Task.steps)` or similar. That is more typing, but it means the query a given endpoint issues is visible in that endpoint rather than emergent from template rendering.

**Why does the downgrade need to drop the enum types explicitly?**

Because a Postgres enum is a schema object in its own right, not part of the table that uses it. `DROP TABLE task_steps` removes the table and leaves `action_type` in `pg_type`. Downgrade then looks like it succeeded, and the next `upgrade` fails with "type action_type already exists" the moment it tries to create it. The bug is invisible until someone runs the cycle, which is exactly why `test_upgrade_downgrade_upgrade` runs upgrade, downgrade, and upgrade again rather than stopping at the first success. It runs against a throwaway database created and dropped inside the test, so a failure cannot leave the dev database half-migrated.

## Follow-ups

- `app/repositories/` is still empty. These models plus the `get_session` dependency are what it will build on.
- No `CHECK` constraints yet: `confidence` between 0 and 1 and `success_rate` between 0 and 1 are both worth adding, but spec section 5 lists only indexes and unique constraints, so they were left out rather than invented.
- `audit_events` cascading with its task is the one deletion rule that may need revisiting if audit retention becomes a requirement.
