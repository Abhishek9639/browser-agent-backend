# B28 - Security hardening

## What was built

The part that goes back over twenty-seven parts of endpoints looking for the gaps, rather than adding a feature. Most of it is small; the value is in the review having happened and being written down.

- `app/core/security_headers.py`: the response headers, and a request body limit.
- CORS tightened from `allow_methods=["*"]` to a named list.
- Rate limits on the approval endpoints and on stream tickets.
- Five validation gaps found and closed, each with a test.
- Screenshot refs carry eight random bytes.
- `make audit` (pip-audit, plus gitleaks when installed) and `.gitleaks.toml`.
- `docs/security.md`: every rule in spec section 10 mapped to where it is enforced and the test that proves it, and the eight prompt-injection layers in the order a hostile sentence meets them.
- 44 tests.

## The five validation gaps

Found by reading every endpoint's inputs against what reaches the database, not by anything failing.

**A control character in an instruction was a 500.** Postgres refuses a NUL byte in a text column outright, so `instruction: "Find the\x00 cheapest flight"` would have failed as an internal error rather than a 400. Now stripped, along with the rest of the C0 and C1 ranges, before the length check, so an instruction made only of control characters is a 400 and not a row.

**A start URL could carry credentials.** `http://user:secret@localhost:8200/` passed the scheme check and the allow-list, because `urlsplit` reads the hostname correctly, and the password would then sit on the task row and in every event about the task. Refused.

**`{"approved": false}` posted to `/approve` was an approval.** Section 6 puts `approved` in the body and the route decides the outcome, so the two can contradict each other. The action on the other side of an approval cannot be undone and either reading might be the one nobody wanted, so both endpoints now refuse a body that disagrees with them.

**An inverted date range returned an empty page.** `?from=February&to=January` read as "you have no tasks", which sends somebody looking for their tasks rather than for the typo in their dates. Now a 400.

**An over-long approval reason was capped but not tidied.** Minor: the reason is now whitespace-normalised, so a reason made of newlines becomes null rather than a blank string on the row.

What I checked and did not change: pagination caps (already 20/100 per decision A17), the enum filters on `?status=`, the `%` escaping on the search term, path parameters (UUIDs, so FastAPI refuses anything else), the grounding description bounds, and the `after_step` lower bound on the WebSocket.

## Key decisions

**Two CSP policies, not one loosened policy.** The API gets `default-src 'none'` with `frame-ancestors`, `base-uri` and `form-action` all denied, because an API answers with JSON and nothing should load, frame or submit to it. Swagger UI needs a CDN script and inline styles, so the documentation routes get their own policy, matched against a fixed set of four paths rather than by prefix: `/docsomething` must not pick up the policy that allows a remote script.

**HSTS in production only.** A development server on plain HTTP sending HSTS teaches the developer's browser to refuse `http://localhost`, and that lesson lasts for the max-age, which is two years.

**`X-Frame-Options` as well as `frame-ancestors`.** Neither is redundant. The header is what a pre-CSP browser reads and the directive is what a current one prefers, and the cost of sending both is twenty bytes.

**The body limit is pure ASGI, not a `BaseHTTPMiddleware`.** The job is to stop reading a body that is too large, and a middleware that has to buffer the request before it can measure it has already spent the memory it was protecting.

**The oversized response is rewritten, not raised.** This was the interesting part. The framework reads the body inside its own validation and turns anything that goes wrong there into a 400 about a malformed body, so an exception raised from the receive channel never reaches the middleware. The counter therefore sets a flag, and the first `http.response.start` is replaced with a 413 while the handler's own body is dropped. That is only possible because nothing has been sent to the client yet, which is the one advantage of being outermost.

**CORS names its methods and headers.** `allow_methods=["*"]` with credentials is both refused by browsers and a statement that any method from that origin is welcome. `PUT` is not in the list because nothing here accepts one.

**Screenshot refs are random, and that is defence in depth rather than the control.** Access is decided by ownership of the task, checked on every read, and the ref never appears in a URL. The random suffix matters for a deployment that later serves the directory statically or syncs it to a bucket, where the name becomes the capability. The pattern accepts refs without the suffix so rows written before this part still resolve.

**`make audit` degrades when gitleaks is missing.** It says so and carries on, because a developer without the binary should still be able to run the audit; CI will install it, so the scan is not optional where it matters. pip-audit runs with `--strict`, so an advisory with no fix available fails the target rather than printing a warning nobody reads.

**Every `noqa: S` in the repository is now listed in `docs/security.md` with its reason.** None of them is a silenced finding; several are the linter recognising a scheme name or an audit action as a password. Listing them makes adding one a visible decision.

## Viva questions

**A page tells the agent to visit a different site and pay someone. Trace what stops it.**

Eight layers, and the answer is that the first three might all fail and it would still not happen.

If the instruction is hidden, it never reaches the model: hidden elements are excluded from the summary. If it is visible, it arrives inside `<page_state>` delimiters, after the goal, described as untrusted, and the system prompt names this exact trick. Suppose the model is persuaded anyway.

The decision is then parsed against a schema, so it has to be one of twelve actions. `navigate` to another site is refused by the domain allow-list before the browser is touched, and again after any redirect. If it instead clicks something on this page, the target has to be an element index that exists in the state the decision was made against. The risk policy reads that target's label and the destination path, and a payment control is HIGH whatever the model said about it, because the final level is the higher of the two. HIGH parks the task and asks a person, and that answer comes through an authenticated endpoint with RBAC, which nothing on the page can reach.

The last three are the ones that matter, because they do not care what the model was told.

**Why is a rejected screenshot request a 404 rather than a 403?**

Because a 403 confirms the task exists. The ownership check comes first, so somebody who cannot see a task cannot learn it exists by comparing the shape of two refusals, and cannot enumerate task ids by watching which ones come back differently.

The same reasoning runs the other way for the approval endpoints: once the caller has been shown the task, there is nothing left to hide, so a 403 about their role is more useful than pretending the path is not there. The line is whether the caller has already been told the resource exists.

**The body limit is on the outermost middleware. What is still unbounded?**

A WebSocket, which is not an HTTP request and skips the limit entirely: a client can send frames as large as the server will buffer. The stream is send-only from our side and any inbound frame other than a pong is ignored, so the exposure is buffer memory rather than anything acted upon, but the limit does not cover it and should.

Inside the limit, what remains unbounded is anything the agent reads rather than anything a client sends: a page can be arbitrarily large, and the summary budget and the screenshot dimensions are what bound that. Those are budgets rather than security limits, which is the right classification, since the page is data the agent chose to fetch from an allow-listed host.

## Follow-ups

- **The rate limiter is per process and in memory.** Two workers allow twice the configured rate and a restart forgets every bucket. It is behind an interface for a Redis implementation.
- **A WebSocket frame is not size-limited.** Noted in the viva answer above; the fix is a check in the receive loop.
- **`docs/security.md` is maintained by hand.** A renamed test makes it wrong and nothing fails. I checked all forty-two test names and thirty-two file paths in it with a script while writing, which is repeatable but not automatic.
- **gitleaks is not in CI yet**, because CI itself is not set up yet. It goes in with the packaging part, along with pip-audit.
- **No dependency pinning policy.** `pip-audit` says the lockfile is clean today; nothing schedules the next check.
- **`/metrics` and the stats endpoint are not rate limited**, deliberately: both are read-only and one is scraped on a schedule, so a limit is more likely to break monitoring than to stop anything.
