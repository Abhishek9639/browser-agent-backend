# B40 - Language gates, popup verification

## What was built

Two fixes from one failed IRCTC booking task. The first step after the page loaded was a language chooser, not a normal popup, and the click that got past it was marked failed.

## Key decisions

The verifier now ignores an expectation that is not a real thing to look for. The planner had written `element_visible "7"` for a step that closed a dialog, taking the 7 from "7 November"; the click worked and the check failed, and the recovery ladder then retried a button that no longer existed. Rather than teach the model never to do that, the verifier stops treating such a value as evidence and uses the action's default (the page changed), the same stance it already took for an empty value. The popup closer learned three more things from the live page: match the visible text when the accessible name is garbled, treat "English" as a safe way through a language gate, and try Escape once when the page is blocked and nothing offers to close it.

## Viva questions

**1. Why does the verifier ignore a one-character expectation instead of checking it?**
It would be true or false by accident, so a pass means nothing and a fail blames a step that worked. A default that checks what the action does is more honest than a check that checks nothing.

**2. Why is choosing English safe to automate when "Accept" is not?**
Choosing a language gives up nothing and can be undone. Accepting cookies or terms is consent on the user's behalf.

**3. Why did the booking stop at "Book now"?**
That is the design: payment and final submission are high-risk and pause for a person. The run was rejected so nothing was booked.
