# B39 - Plan preview

## What was built

An outline of the expected steps, produced once before the first action, stored on the task, and sent to the client so it can show "step 2 of about 6" instead of a progress bar that has no idea how long the task is.

## Key decisions

The request was to have the agent plan the whole task first. The spec says the model proposes exactly one next action per turn, and the planner prompt forbids planning several steps ahead, because the page changes after every action: the first Internshala run met a sign-up popup no outline could have named. So the outline is a forecast and never an instruction. It is stored before it is published, the same rule as steps, so a reconnecting client gets it from the database. It is opt-in because it costs one more model call, which matters on a free tier with a daily quota, and because scripted tests would otherwise have the call consume their answers. A failed outline is silent by design.

## Viva questions

**1. Why not execute the plan instead of using it for display?**
A plan written before the first page loads cannot know what the pages will contain. Executing it would turn every popup or layout change into a failed step, which is what the one-action-at-a-time design avoids.

**2. Why store the plan before publishing it?**
A client that reconnects mid-task is caught up from the database. If the event went out first and the write failed, the live view would show a plan the database never had.

**3. Why is it off by default?**
It spends one extra model call per task. On a quota of twenty requests a day that is a real cost, so it is a choice made in the environment, not a surprise.
