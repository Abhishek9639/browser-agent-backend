# B05 - Repositories and audit service

## What was built

A data access layer over the B04 models, and the audit service that is the first consumer of it.

- `app/repositories/base.py` - generic `BaseRepository[Model]` and the `Page` result.
- Ten concrete repositories, grouped by aggregate to match `app/models/`.
- `app/repositories/unit_of_work.py` - every repository over one session.
- `app/services/audit.py` - `AuditService.record()` and the `AuditAction` names.
- `app/core/redaction.py` - masking rules extracted so logs and audit rows cannot drift.
- 32 integration tests against real Postgres.

## Who commits

One rule: **whoever opens the session commits it, and nobody else does.**

```
Database.session()        opens, commits on clean exit, rolls back on exception
  └─ get_session          FastAPI dependency, yields inside it
       └─ UnitOfWork      bundles repositories over that session
            └─ services   read and write, never commit
                 └─ repos flush, never commit
```

In a request, `get_session` opens the session inside `Database.session()`, which commits on a clean return and rolls back on an exception. One request is one transaction: a handler that raises halfway leaves nothing half-written, and no handler has to remember to roll back.

In background work there is no request, so the caller opens the session and the same context manager commits it:

```python
async with database.session() as session:
    uow = UnitOfWork(session)
    step = await uow.task_steps.add(TaskStep(...))
    await AuditService(uow.audit_events).record(AuditAction.TASK_CREATED, task_id=task.id)
# committed here, or rolled back if the block raised
```

That matters for the agent loop, which will write a step, an LLM decision, a verification and possibly recovery attempts for a single iteration. Those belong in one transaction: spec section 6.1 requires a step to be in the database before its WebSocket event is published, and a client that receives a `step` event must find the whole record if it then asks for it over REST.

**`UnitOfWork` has no `commit()`, on purpose.** Offering one invites a service to commit half a change, which is the exact failure the pattern exists to prevent. A test asserts the method does not exist, so nobody adds it for convenience later.

**Repositories flush, they do not commit.** `add()` flushes so the caller immediately gets server-side defaults, the primary key and `task_number`. Flushing sends the INSERT inside the open transaction; it is still rolled back if the request fails. `test_add_does_not_commit` proves this by adding a row, asserting it is visible, rolling back, and asserting it is gone.

## Key decisions

**`get_owned` raises `NotFound`, not `Forbidden`.** Returning 403 for someone else's task confirms the id exists. Given sequential-ish ids, that lets an attacker enumerate task ids and learn how much traffic the system carries, and whose. Returning 404 for both "does not exist" and "not yours" leaks nothing, and a test asserts the two are indistinguishable in code, status and message shape. Admins bypass the check, per the RBAC in spec section 6.

**Text search escapes LIKE wildcards.** A user searching for `100%` would otherwise match every row, because `%` is the wildcard, and `_` would match any single character. `escape_like` neutralises `\`, `%` and `_`, and the comparison passes `escape="\\"`. Two tests cover it, because this is the kind of thing that looks fine until a user types a percent sign.

**The count comes from the same statement as the rows.** `paginate` builds the count from `stmt.order_by(None).subquery()` rather than a separately assembled query. If the filters were written twice they would eventually diverge, and a total that disagrees with the rows is a bug users notice immediately when the last page is empty.

**Redaction moved out of `logging.py`.** It was there in B02 because logging was the only consumer. `audit_events.metadata` is as readable as a log line to anyone with database access, and spec section 10 covers both, so the rules now live in `app/core/redaction.py` and both import from it. A test asserts an audit row and a log line mask the same payload identically, so the two cannot drift.

**`AuditAction` is constants, not an enum.** Spec section 5 types `action` as text. An enum would mean a migration every time an audited action is added, which is friction in the wrong place: unlike the action allow-list, there is no safety property that depends on the set being closed.

## The bug the tests caught

`CachedFlowRepository.upsert` uses `INSERT ... ON CONFLICT DO UPDATE ... RETURNING`. The SQL was right and Postgres updated the row, but the method returned the *stale* object: SQLAlchemy's identity map already held that `CachedFlow` for this session and handed it back with its pre-upsert values, ignoring what `RETURNING` produced. The test compared the returned `action_sequence` against what was written and failed. Fixed with `execution_options(populate_existing=True)`, which tells the ORM to overwrite the mapped instance from the returned row.

Worth remembering: with an identity map, "the database is correct" and "the object I am holding is correct" are different claims.

## Viva questions

**Why not let repositories commit? It would be less code.**

Because a commit is a decision about a *unit of work*, and a repository only sees one table. If `TaskRepository.add` committed, then creating a task, reserving credits and writing the audit row would be three transactions, and a failure in the third would leave a task that was never paid for and has no audit trail. Keeping commits at the session boundary means the caller decides what is atomic. It also makes tests fast and isolated: the fixture wraps each test in a transaction it rolls back, which only works because nothing underneath commits.

**What does `lazy="raise"` from B04 force this layer to do?**

It forces every query to state what it loads. `TaskRepository.list_for_user` returns tasks with no steps loaded, so a caller that wants steps must ask for them: either `TaskStepRepository.list_for_task`, or a future query that adds `selectinload(Task.steps)`. In exchange, nothing silently issues a query per row while a response is being serialised. The cost is visible in the repository, which is where it should be, rather than emergent at render time.

**Why is pagination `page`/`page_size` rather than a cursor?**

Spec section 6 defines the endpoint as `GET /tasks?status=&from=&to=&q=&page=`, and the frontend's task history screen shows a page count, which needs a total. Offset pagination gives that directly. Its weaknesses are real, deep offsets are slow and rows can shift between pages when new tasks arrive, but at the scale of one user's task history neither matters. A cursor would be the right call for the step stream, which is append-only and potentially long, and there `list_after(task_id, step_number)` already is a cursor: the step number is a natural, stable, per-task sequence.

## Follow-ups

- `app/services/` has only the audit service. Task, approval and auth services arrive with the endpoints that need them.
- `Page` is a dataclass, not a Pydantic model, so it stays out of the API layer's serialisation concerns. The response schema that wraps it belongs in `app/schemas/`.
- `ApprovalRepository.list_expired` takes `cutoff` as `object` because the timeout job that computes it does not exist yet. It should be narrowed to `datetime` when that lands.
