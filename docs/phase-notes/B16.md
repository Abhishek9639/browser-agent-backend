# B16 - Orchestrator core loop

## What was built

The loop from spec section 4.2, on the happy path, with every part that does not exist yet named as an interface rather than left as a gap in the code.

- `app/agent/orchestrator.py`, `app/agent/contracts.py`, `app/agent/browser/agent_browser.py`.
- `docs/agent.md` gains a sequence diagram of one iteration.
- 43 tests: 34 unit against fakes, 9 integration against real Postgres and real Chromium.

## Key decisions

**The screenshot is written before the rows, and the rows before the event.** Both orderings are load-bearing and neither is arbitrary. Storage is not transactional, so one of the image and the rows has to go first: writing the image first can leave an orphaned file after a rollback, which `delete_task` sweeps and nobody notices, while the other order leaves a committed row whose `screenshot_ref` points at a file that was never written, which is a broken image in the live view and in every replay of that task afterwards. Committing before publishing is what spec section 6.1 relies on when a client reconnects with `after_step`: publish first and there is a window, however short, in which a client can be told about a step it can never fetch.

**Six collaborators, six do-nothing defaults, one file.** Verification, recovery, grounding, risk policy, approvals, cache, sessions. Putting the defaults together in `contracts.py` rather than scattering them into the packages that will own them means "what is not built yet" is one file you can read end to end. Each later part deletes one default and touches nothing else in the loop.

**The approval gate refuses instead of doing nothing.** It is the one default that is not a no-op. A gate that auto-approves is indistinguishable from working software until the day somebody forgets to replace it, and then an agent buys something. Refusing fails the task, which is visible in the first five minutes and costs nothing. The integration test asserts the browser was never asked, because an approval that arrives after the click is not an approval.

**The stub verifier does not write the word "stub" into the database.** The brief asked for `method="stub"`. `verifications.verification_method` is a Postgres enum of the six section 4.5 outcome types, so that would mean a migration to widen a spec-defined enum for a scaffold, and a harder one to narrow it again later. The stub reports the outcome type the planner asked for, which is the honest answer to "what was supposed to be checked", and records `verifier: stub, checked: false` in `actual_outcome`, the free-form column that exists for exactly this. Nothing is lost and no row can later be mistaken for a real check.

**Failure reasons are ours, never the exception's.** `str(exc)` on a Playwright timeout carries the URL it timed out on, and that URL can carry a session token. Spec section 10 says none of that leaves the process, so the loop maps exception types to sentences written here and logs the real detail at `exception` level where nobody untrusted reads it. There is a test that plants a token in an exception message and asserts it reaches neither the database, the outcome, nor any event.

**`raw_output` needed the same redaction as the column next to it.** Easy to miss: the model's decision is stored verbatim for debugging, and a decision that types a password carries that password in its `value` field. Getting `value_redacted` right and leaving `raw_output` alone would satisfy section 10 in one column and break it in the next.

**Running out of time and running out of steps are different states.** `TIMED_OUT` and `EXECUTION_FAILED`. A task that ran out of seconds may well succeed on a retry; one that spent twenty-five steps without reaching an answer is stuck, and retrying it unchanged spends twenty-five more. Reporting both the same way hides that from whoever decides whether to retry.

## Four bugs the tests found

**`max(HIGH, MEDIUM)` is `MEDIUM`.** Spec section 4.2 says the final risk is `max(deterministic, LLM)`, and `RiskLevel` is a `StrEnum`, so the obvious transcription compares alphabetically and quietly downgrades every action that a deterministic policy escalates but the model called low risk. That is a security bug that would have shipped looking exactly like the spec. `RiskLevel.rank` and `RiskLevel.highest` now make the ordering explicit, and the test that catches it fails on the naive version.

**The step status ignored whether the action ran.** With a stub verifier that passes everything, a click that never found its element was being recorded as `VERIFIED`. The loop now short-circuits: if the action did not run there is nothing to check, so it writes a failed verification itself rather than asking a verifier that would say yes. Recovery still gets its turn, which is what spec section 4.8 is for.

**Vision steps were never counted.** `_iterate` always leaves by raising, so the value it returned was never read and the credit total was always the plain per-step count. Now accumulated in a small mutable tally the caller still holds.

**A cancel landing mid-step was reported as an internal error.** The loop noticed cancellation between iterations, but a cancel arriving while a step was in flight made the next `_set_status` raise `IllegalTransition`, which the generic handler turned into "internal error" even though the outcome was right. This is the exact race the B15 note described. `_set_status` now treats an already-terminal task as the other writer having won, and stops cleanly.

## The integration suite was broken and I had not noticed

`make test-int` did not run a single test. The settings isolation I added in B14, to stop unit tests reading a developer's `.env`, also hid `.env` from `integration_settings`, and `.env` is where the Postgres port lives on this machine, because Homebrew already holds 5432. Every integration test failed to connect. It stayed hidden because B14 and B15 were verified with `make check`, which runs unit tests only, and the failure is invisible until someone runs the other target.

Two fixes. `real_environment()` puts `.env` and the exported variables back for the block that builds `integration_settings`, with the reasoning written down: a unit test must not depend on whose machine it runs on, and an integration test depends on a real database by definition. And `api_app` now takes its database URL from those settings, because the failed-login audit deliberately opens a connection of its own and it has to reach the same Postgres as the rest of the test.

The lesson is about the gate rather than the fixture. `make check` is the definition of done for a part, and it does not cover the integration suite, so a regression there can survive two parts. Worth deciding whether `check` should include it.

## Viva questions

**Why is the step event published after the commit rather than inside the transaction?**

Because publishing inside the transaction promises something the transaction might not keep. If the commit then fails, the client has already been told about a step that does not exist and never will, and it has no way to find that out: the sequence number it saw is real, so a reconnect asking for everything after it gets nothing back and the client concludes it is up to date.

Committing first gives the opposite failure, and it is the harmless one. If the process dies between the commit and the publish, the client misses a step it can still fetch. Spec section 6.1's reconnect path exists for exactly that: the client asks for everything after the last sequence it saw, and the database, being ahead, can answer. The invariant is that the database is never behind the live view, and the write order is the whole of its enforcement.

**Every collaborator is an interface with a default that does nothing. Is that not just building indirection for code that does not exist?**

It would be if the defaults were placeholders that get deleted. They are not: each one is the honest minimal behaviour, and two of them are decisions in their own right. The approval gate refuses rather than approving, which is a safety position rather than a stub. The stub verifier passes but records that it did not check, so no row from this period can later be mistaken for a verified one.

The concrete payoff is testability, which was not theoretical. The loop has paths that are hard to reach with real components: a browser that fails an action, a model that cannot produce a valid decision, a verifier that always fails, a page that changes between perception and the click, a database that refuses every write. All of those are one small class in a test. Without the seams, most would need a fault-injection layer somewhere worse.

**The loop takes a screenshot on every step, including the `done` step. Is that not waste?**

It costs one capture and a few tens of kilobytes per step, and it buys two things the spec asks for. The live view shows the page beside each entry in the activity log, and section 8 wants a user to scrub back through steps without leaving the live view, which needs an image per step rather than only the last one. The step event carries the image inline so the live view needs no second request.

The `done` step is the one worth arguing about, since nothing happened. It is captured anyway because the final frame is the evidence for the answer: a user reading "cheapest flight is Rs 4,299" wants to see the page that was on screen when the agent said so. The alternative, special-casing `done`, saves one frame per task and makes the last entry in the log the only one that cannot be inspected.

## Follow-ups

- Nothing calls `Orchestrator.run` yet. A task runner with the section 4.2 concurrency limits is the next piece, and it is what will own the browser lifetime.
- The action path resolves a target by the collector's stamp and hands it to the driver as a plain selector, so `page.locator` only searches the main frame. `locator_for_index` already walks every frame; wiring the driver to use it is what iframe targeting needs.
- `_current_status` costs one query per iteration to notice a cancel. Fine at this size, worth revisiting if it shows up.
- Credits are counted, not reserved or settled. The numbers in the final event are what billing will reconcile against.
- Approval currently ends the task when refused. Once approvals are real, a rejection should still record the step it was asked about.
