# B33 - Groq provider and fast rate-limit fallback

## What was built

A Groq adapter and a change so a rate-limited primary falls back at once. Set `LLM_PROVIDER=gemini`, `LLM_FALLBACK_PROVIDER=groq` and `GROQ_API_KEY`.

## Key decisions

The fallback chain already existed; the gap was a provider to fall back to, and the primary sleeping through its retry-after before the fallback was tried. With a fallback configured, rate limits now skip the retry loop. Groq has its own model settings because `LLM_MODEL` belongs to the primary. JSON mode is used because strict schemas are model-specific on Groq; the planner's own validation is the real enforcement.

## Viva questions

**1. Why skip retries on a rate limit when a fallback exists?**
A quota error usually clears in tens of seconds, and waiting stalls the task. The fallback exists for exactly that case. Other failures are still retried, since they are often momentary.

**2. Why does Groq not use LLM_MODEL?**
That setting names the primary's model. A Gemini model name sent to Groq would fail every fallback call.

**3. Why no new dependency?**
Groq speaks the OpenAI protocol, so the `openai` SDK already in the stack is pointed at Groq's base URL.
