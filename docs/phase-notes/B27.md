# B27 - Metrics, stats overview and log hygiene

## What was built

The part that makes the previous twenty-six measurable. Spec section 9 names ten KPIs and until now every one of them could only be obtained by running the benchmark; they are now published continuously.

- `app/core/metrics.py`: sixteen collectors on their own registry, and `GET /metrics` in Prometheus text.
- `GET /api/v1/stats/overview`: the same KPIs per user, computed from the rows rather than from process counters, which is what the history page needs.
- Log context bound rather than passed: `task_id` for a run, `step_number` for a step, `request_id` already existed.
- `docs/observability.md`: what is published, what to query, and seven alert rules.
- 30 tests, including a scan of every log line a full mock task produces.

`prometheus-client` is a new dependency. It is not in the spec section 3 list, but section 6 requires `GET /metrics` in Prometheus text format, and the brief asked for it by name.

## Key decisions

**No metric is labelled by anything unbounded.** Not a task id, not a user id, not a URL. A label whose values come from user input is a memory leak with a graph attached, and it is the standard way to take down the system you were trying to watch. There is a test that enumerates the registry and fails if any collector grows one of those labels, because the tempting moment is six months from now when somebody wants to see one task's numbers.

**The route label is the template, and an unmatched request is `unmatched`.** `/api/v1/tasks/{task_id}` is one series; `/api/v1/tasks/<uuid>` would be one per task. Unmatched requests matter just as much: a scanner probing a thousand paths would otherwise create a thousand series.

**Recovery is counted per failed step, not per attempt.** Same definition as the chaos harness, and for the same reason: a step rescued on the third rung is one success, not one success and two failures. This is the third time the distinction has come up in this project and the first time it is enforced in code that runs in production rather than in a test harness.

**A ratio gauge, against my own preference.** Ratios belong in PromQL, where the window is part of the question. `recovery_success_ratio` exists anyway because section 9 names it as a KPI and the stats endpoint reports it; the two counters it is derived from sit next to it, and the documentation says to prefer them.

**One choke point for model calls.** `record_response` and `record_failure` live in `app/agent/llm/base.py`, and the two callers are the planner and visual grounding. Instrumenting each adapter would mean the next adapter is the one that gets forgotten.

**A failed model call is timed as well as counted.** Dropping timeouts from a latency histogram makes a provider look better the worse it gets.

**Cache lookups have three outcomes, not two.** `hit`, `miss` and `ineligible`. A flow that exists and is below the success-rate threshold is not a hit: counting it as one would make the rate describe how often a signature matched rather than how often the cache saved anything.

**The stats endpoint computes from rows, not from counters.** Process counters reset on deploy and know nothing about work done before this process started. A user's history has to survive a restart, so the endpoint queries the tables and the metrics stay for operators.

**Every rate is null, never zero, when there is nothing to divide by.** Zero claims that nothing succeeded, which is a different thing to show a user than an empty history, and once it reaches JSON the frontend cannot tell them apart.

**`scope=all` is refused rather than narrowed.** A non-admin asking for the global view gets 403, not their own numbers under a global heading.

**The cache hit rate counts tasks with a step that has no `llm_decisions` row.** `tasks.cache_flow_id` is not the test: it is set both when a task replays a flow and when a task stores one, so using it would report every completed task as a hit. The absence of a model call is what a replayed step leaves behind, and it is the same evidence the B25 tests assert on.

**Loggers are no longer cached on first use.** This was the price of making the section 10 guarantee testable. `cache_logger_on_first_use=True` binds each module's logger to whatever processor chain existed the first time it logged, which makes the pipeline unobservable from a test: nothing can capture what a real run emits. A guarantee nobody can check is not a guarantee, and the cost is a dictionary lookup per log call.

## Two bugs this part found

**Unlabelled counters survived `reset()`.** `clear()` empties a collector's label map, which is everything for a labelled metric and nothing at all for an unlabelled one, because those keep their value in a child of their own. One test's recovery episodes were turning up in the next test's total. There is now a test for the reset itself.

**`capture_logs` would have made the log-hygiene test vacuous.** structlog's own helper replaces the whole processor chain, which removes both the redaction processor and the contextvars merge, the two things the test exists to check. It also passed at the suite's default `CRITICAL` level by capturing nothing at all and calling that clean. The fixture now replaces only the renderer at the end of the real chain and lowers the level for its duration. Both failures would have produced a green test that proved nothing, which is worse than no test.

## Viva questions

**Why not label metrics by task id, when that is obviously the thing you want to filter by?**

Because Prometheus keeps one time series per label combination, in memory, for as long as its retention window. A thousand tasks a day with a task id label is a thousand new series a day, growing without bound, and the exposition itself grows with them until scraping becomes the slowest thing the service does. This is the single most common way a team's own instrumentation causes the outage it was installed to detect.

The per-task question is a logs question, and the logs are built for it: every line inside a run carries its task id, so `event="action_failed"` grouped by `task_id` answers it without adding a series. Metrics answer "is this happening more than usual", logs answer "what happened to this one", and the observability page says which to reach for.

**The stats endpoint and `/metrics` both report a recovery rate. Which one is right?**

Both, for different questions. `/metrics` counts what this process has seen since it started, which is what an alert needs: it resets on deploy, and that is correct behaviour for something asking "is it broken right now". The stats endpoint queries the rows, so it survives restarts and covers work done by processes that no longer exist, which is what a user looking at their history needs.

They are computed the same way on purpose, per failed step rather than per attempt, so a discrepancy between them means a real one: rows written by another worker, or a process that has just restarted.

**What stops a secret reaching the logs, and how do you know?**

Three layers. Values are masked at the point they are collected, so a password field's value is `••••` before it reaches any Python that could log it. A redaction processor sits last in the chain and masks anything under a key that looks sensitive, with an exact allowlist for the handful of names that contain a sensitive-looking word and are always counts. And the logger call sites do not pass page content or screenshots in the first place.

How I know is the third layer, which is the part that is new here: a test runs a whole mock task against a page containing a password field, a card number and a sentence of personal information, captures every line through the real processor chain, and asserts that none of the three strings appears anywhere. It also asserts that the capture found something, because a scan that captures nothing passes trivially, and it did exactly that on the first attempt.

## Follow-ups

- `/metrics` is per process. Two workers publish two independent sets of counters and the gauges describe one process each, which is what Prometheus expects from a scrape target, but it means `active_tasks` is not the deployment's total until the scraper sums it.
- `recovery_success_ratio` is process-lifetime, so it moves slowly and never forgets. The counters beside it are the ones to alert on.
- No metric covers the browser itself: no page load time, no screenshot size, no context launch duration. All three are logged, and worth promoting if the driver ever becomes the suspect.
- The stats endpoint runs eight queries per call. Fine at this size and the obvious thing to cache if the history page ever gets busy; a thirty second cache would be invisible to a user and would make it one query per thirty seconds per scope.
- Credits are computed from step and vision counts using the section 7 prices, mirrored in two places now. The ledger lives in the payments service, so this is an estimate of what this service believes it spent rather than a statement of what was billed.
