# B07 - Refresh rotation, RBAC, rate limiting

## What was built

The session half of authentication: a refresh cookie that rotates on every use and detects theft, role checks that distinguish "who are you" from "you may not", and throttling on the two endpoints an attacker hammers.

- Refresh cookie on login; `POST /auth/refresh`, `POST /auth/logout`, `GET /auth/me`.
- `require_roles(*roles)`.
- `app/core/rate_limit.py`: `RateLimiter` plus an in-memory token bucket.
- `scripts/create_admin.py`.
- 12 unit tests, 39 integration tests.

## Key decisions

**The refresh token is opaque, not a JWT.** Its whole job is to be revocable, and a self-contained token cannot be revoked without a server-side list. Since the list is needed either way, the token carries no claims and is just 384 random bits.

**Stored as SHA-256, not argon2.** Slow hashing defends a low-entropy secret a human chose against offline guessing. This value has nothing to guess, and refresh is a hot path needing an indexed equality lookup. A dump of the table still cannot be replayed, which is the property that matters. Using argon2 here would be cargo-culting the password rule into a place it does not apply.

**Rotation is single-use, and reuse destroys the chain.** Every refresh invalidates the presented token, which turns a stolen cookie from a seven day pass into a race. When a revoked token comes back, two parties hold one cookie and there is no way to tell which is the thief, so every session for that user dies. The legitimate user being logged out is the cost; the alternative leaves an attacker with a live session.

**ADMIN is not implied by `require_roles`.** Every route lists the roles it accepts, so reading the route tells you who can reach it. Implicit admin is convenient right up to the first route where it was not intended.

**A token bucket, not a fixed window.** A fixed window lets a caller spend the whole quota in the last second of one window and again in the first second of the next, which is twice the intended rate across the boundary. The bucket refills continuously.

**`X-Forwarded-For` is ignored unless explicitly enabled.** Any client can send that header, and trusting it by default hands every caller a fresh bucket, which defeats the limit completely. `RATE_LIMIT_TRUST_FORWARDED_FOR` exists for when there really is a proxy in front.

## The bug that changed the design

The first version of reuse handling copied B06's failed-login pattern: open a second transaction, revoke the chain there, then raise so the 401 propagates.

The integration tests returned 500. The traceback showed a foreign key violation on `audit_events.actor_id`: the second transaction could not see the user, because the user row lived in the request's transaction and was not committed.

That is not only a test artifact. It exposed the real constraint: **the chain revocation reads and updates rows that belong to the request's transaction.** A second connection cannot see them, so it cannot revoke them either. The pattern was wrong for this case, not just awkward.

The fix inverts the control flow. The revocation runs in the request's own transaction, and the route catches `RefreshTokenReuse` and *returns* the 401 rather than raising it. The request finishes normally, so the transaction commits and the revocation persists.

B06's failed-login audit keeps its separate transaction, and the distinction is principled: that write depends on nothing in the request's state, being one row with no actor and no foreign key.

## Two smaller findings

**The redaction rule was eating the audit trail.** `TOKEN_REUSE_DETECTED` recorded `token_id`, and the key contains "token", so the stored metadata read `[REDACTED]`, masking the exact identifier a security review would need. These are row ids, not secrets. Renamed to `session_id`, which is also the better name: a `refresh_tokens` row is conceptually a session. The over-broad rule stays, because over-redacting is cosmetic and under-redacting is an incident.

**Postgres `now()` is the transaction timestamp.** A test ordered refresh tokens by `created_at` and failed intermittently, because both rows were written in one transaction and `func.now()` is `transaction_timestamp()`, identical for both. Worth remembering: `audit_events` ordered by `timestamp` has the same ambiguity for events written in a single request.

## Viva questions

**Someone steals a refresh cookie. Walk through what happens.**

They have at most until the legitimate client next refreshes. Whoever refreshes first gets a new cookie and invalidates the old one. When the loser presents the now-revoked token, the server sees a revoked row and cannot tell which party is the thief, so it revokes every session for that user. If the attacker refreshed first, the real user is logged out on their next refresh and logs back in with a password the attacker does not have, cutting the attacker off. If the real user refreshed first, the attacker's replay triggers the same revocation. Either way the attacker's window is one rotation, not seven days. Without rotation the stolen cookie would be valid for the full TTL with nothing to detect it.

**Why not return 403 for a valid token whose role is insufficient, but 401 for no token? Is that not leaking?**

The two answer different questions. 401 means the request carried no usable identity; the client should authenticate and retry, and that is actionable. 403 means the identity is established and the answer is still no; retrying will not help. Collapsing both into 403 would make an unauthenticated client retry forever, and collapsing into 401 would send an authenticated one to the login page it just came from. What we do avoid leaking is *existence*: `get_owned` returns 404 rather than 403 for someone else's task, because there the id itself is the secret. Here the route is public knowledge and only the role is in question.

**The rate limiter is in-memory. What breaks when you scale to two workers?**

Each process keeps its own buckets, so the effective limit doubles: five logins per minute per worker, ten in total, and a client hitting a load balancer round-robins between them. That is fine for the OJT deployment, which runs one process, and it is exactly why the limit sits behind an interface. The fix is a Redis-backed `RateLimiter` implementing the same two methods, swapped in at startup, with no change to any route. The wrong fix is dividing the numbers by the worker count, which breaks the moment the deployment scales again. There is a second, subtler issue: the buckets are lost on restart, so a deploy resets everyone's quota. Acceptable here, and also fixed by moving the state out.

## Follow-ups

- `RATE_LIMIT_TASK_CREATE_PER_MINUTE` is defined and unused until `POST /tasks` exists.
- Rate limiting is keyed on IP only. Login could additionally be keyed on the submitted email, so one attacker cannot lock out an account by spraying it from many addresses, and so a distributed attack on one account is caught.
- `refresh_tokens` rows are never pruned. Expired and revoked tokens accumulate; a periodic delete belongs with the other background jobs.
- The reuse response currently returns a plain 401. Telling the user their sessions were revoked for safety would be kinder, but says more to an attacker; worth a product decision.
