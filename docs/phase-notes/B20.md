# B20 - Deterministic verification

## What was built

The agent can now tell a click that worked from one that missed. Until this part every step passed, which meant the recovery ladder had nothing to trigger on and a task could report success having done nothing at all.

- `app/agent/verification/verifier.py` and `app/agent/browser/stability.py`.
- The stub verifier is deleted and the orchestrator uses the real one.
- 48 tests: 38 over the checks and defaults, 5 driving the settle race against a real browser, 2 scoring the labelled set, and 3 in the loop suite.

## Key decisions

**No model, ever.** ADR-004 and spec section 4.7. Every check is a comparison between two page states, and every one is reproducible from the two rows that get stored. The reasoning is not a general preference for determinism: a model that is wrong about what a click did is exactly the model that will confidently report it worked, so letting it mark its own homework converts one error into a silent one. There is a test that reads the module's own source and fails if the word appears, because a comment saying "does not call the LLM" is not enforcement.

**The verifier takes page states, not the cheap snapshot.** Half the checks need the element list: whether a control is visible, what an input now holds, whether a checkbox is ticked. That turned out to make the loop cheaper rather than more expensive. The state read after an action is the state the next step plans against, so carrying it forward means one perception per step instead of two, and the browser snapshot is no longer taken at all.

**Eight checks, six stored methods.** `verifications.verification_method` is a Postgres enum of the six section 4.5 outcome types, and the verifier runs a few more checks than that because the defaults need them: a scroll has no outcome type of its own and neither does "the extract came back empty". The precise check goes in `actual["check"]` and the stored method stays one of the six. Same call as the stub in B16 and for the same reason: an enum column should not grow to hold a detail that belongs in JSON. The mapping is deliberate rather than convenient. Section 4.7 writes "URL change/contains" as one item, so both URL checks store as `url_contains`. A control's checked or selected state is its value, so `element_state` stores as `value_equals`.

**Defaults fire when the declared expectation is useless, not only when it is absent.** The schema makes `expectedOutcome` required, so something is always declared. It is not always checkable: a model that asks for `text_present` with an empty value has declared a check that passes on every page in the world, and treating that as verification is worse than having none. So an expectation that needs a value and was given an empty one falls back to the default for that action.

**A masked field is taken on trust.** The collector masks secrets at source, so after typing a password the real value is not in the page state to compare against and never will be. Failing every password field instead would leave the agent unable to log in to anything. The field still has to be there; what cannot be checked is only its contents.

**The page has to stop moving before it is read.** A click that triggers a fetch is not finished when `click()` returns. Network idle or a DOM quiet for 300 ms, whichever comes first, capped at three seconds. The cap matters as much as the wait: a page with a carousel or a polling widget never goes quiet, and failing a step because the site has an animation on it would be worse than reading slightly early. The helper reports whether it settled and never raises.

**`element_state` is the check for a stateful control.** Clicking a disclosure flips `aria-expanded` and changes nothing else, and `expanded` is not part of the DOM hash, so `dom_changed` would call a working click a failure. Checkboxes are in the hash and would have passed anyway, but the state check says something more precise about what happened.

## Two things the tests found

**`text_present` could not see most text.** The first version searched the perception summary and the element list, both of which are interactive elements only. The end-to-end run then failed: the form writes "Searched: Delhi" into a paragraph, and a paragraph is not a button. Section 4.7 means text on the page, so `PageState` now carries the page's visible text, clipped, and the check looks there first. It is deliberately not sent to the model, which still gets only the compact summary.

**`url_changed` was almost unreachable.** I had it as the fallback for an empty `url_contains`, but the action defaults always replaced an empty expectation first, so nothing ever reached it except a navigate to a URL with no parseable host. Going back has exactly one observable effect, so `go_back` now defaults to it. Writing the test for a check is a good way to find out whether the check can happen.

## The slow-page test

Worth describing because it tests the race rather than the helper. The fixture page renders its results 700 ms after the click. One test clicks and perceives immediately and asserts the DOM hash is unchanged and the new button is absent, which is the bug reproduced. The next clicks, settles, perceives, and asserts both the other way. A third runs the real verifier over both and asserts the same click verifies false early and true late.

SkyFare's `delay` chaos is a server-side delay before the response, which navigation already waits for. The race worth testing is the client-side one, where the response has landed and the page is still building itself from it, which is what the fixture reproduces.

## Viva questions

**Why is a false positive worse than a false negative here, and how does the design reflect that?**

A false negative says a step failed when it worked. The agent recovers from a success: it burns steps and tokens, it may repeat an action that was already done, and in the worst case it fails a task that had actually finished. Expensive and visible.

A false positive says a step worked when it did not. The agent carries on from a page that is not where it thinks it is, and every step after that is planned against a wrong premise. It is not just one bad step, it is everything downstream, and nothing in the run ever notices. That is why the labelled set scores the two separately instead of reporting one accuracy number, why the set is half negative cases rather than mostly successes, and why the checks fail closed: an expectation that cannot be checked becomes a different check rather than an automatic pass.

**The planner declares what it expects, and the verifier sometimes ignores that and uses its own default. Is the verifier not second-guessing the model?**

It is, and that is the point of ADR-004. The declared expectation is a hint from the component whose reliability is being checked, so treating it as authoritative would put the model back in charge of its own assessment by a side door. A model that wants a step to pass can declare `dom_changed` on a page that changes constantly.

The line I drew is narrower than full second-guessing: the declared expectation is honoured whenever it can actually be checked, and replaced only when it cannot. `text_present` with nothing to look for is not a weaker check, it is not a check at all, and substituting the action's default is strictly more information than passing it. What the verifier does not do is override a checkable expectation because it disagrees with it, since that would make the planner's declaration pointless and the behaviour hard to reason about from a stored row.

**Every check compares two snapshots. What can this design never catch?**

Anything whose evidence is not in either snapshot. Three kinds in particular. An effect that is real but invisible: a click that fires an analytics call or writes to storage looks identical to a click that did nothing. An effect that lands after the settle cap: a page that takes four seconds to render is read at three and the step is failed, which is a false negative the cap makes unavoidable and the setting makes tunable. And an effect on something the collector does not report: it returns interactive elements plus the page text, so a change confined to, say, an image or a canvas is invisible to the DOM hash.

The mitigation for the third is the page text, which is why `text_present` searching it matters more than it first looks. For the first two the honest answer is that the verifier is doing what it can see, and the layer that catches what it cannot is recovery deciding whether a failed verification is worth retrying.

## Follow-ups

- An unverified step fails the task. Recovery is the next part and is where a failed verification should instead become an attempt to fix it.
- `element_state` is flip detection, because the section 4.5 schema has no outcome type the planner could use to ask for a specific state. If it ever gains one, the comparison goes in the same function.
- The settle cap is a fixed three seconds. A slow site would want it per domain, and the page that needs four seconds is currently a false negative.
- The accuracy set is hand-built page states. Cases captured from real runs against SkyFare with its chaos toggles on would be a harder test, and the labelled set is the right shape to hold them.
