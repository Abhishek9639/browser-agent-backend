# B24 - Multi-tab session manager

## What was built

The tab bookkeeping was already in the driver, as three private methods and a counter. This part lifts it into something with a name and a contract, and then makes the planner able to use it.

- `app/agent/browser/sessions.py`: `TabSessionManager`, one per task. Stable ids, the active tab, popup capture, per-tab last `PageState`, a tab limit, and orphan cleanup when the task ends.
- `new_tab`, `switch_tab` and `close_tab` go through it. The driver no longer keeps a tab dictionary of its own.
- The section 4.6 header names what each tab holds: `Tabs: t1 Delhi to Bengaluru | SkyFare (active), t2 SpiceJet SG-419 | SkyFare`.
- Three tab checks in the verifier: `new_tab_opened`, `active_tab_changed` and `tab_closed`.
- `planner_v2.md`, with a section on tabs. v1 is untouched and still loadable.
- 24 tests, plus the SkyFare `newtab` journey in the chaos suite.

## Key decisions

**Closing the active tab lands on the most recent remaining tab, not the oldest.** The old code did `next(iter(self._pages), None)`, which is the first tab ever opened. An agent that opened a detail view from a results page and then closed it wants the results page, which is the tab before this one. On a two tab journey the two rules agree, which is why this survived until something looked at it.

**A tab id is never reused.** Ids come from a counter that only goes up, so closing `t2` and opening another gives `t3`. Reuse would make the planner's own transcript lie: "switch to t2" earlier in the conversation and "switch to t2" now would name different pages and nothing in the history would say so.

**Opening a tab is not switching to it.** A `target="_blank"` link gets its tab tracked and leaves the agent where it was. Moving the agent because the page opened a window would let any site redirect the agent by putting an attribute on a link, and it is also just wrong about what happened: the click did open a tab, and whether to read it is a decision. `new_tab`, which the agent asked for, does switch.

**The header carries labels, not just ids.** `Tabs: t1, t2` tells a planner nothing about whether t2 is the flight detail or an advertisement, and the switch decision rests on exactly that. A tab that has not been perceived yet prints as its bare id, which is honest: perception is the only thing that knows what a tab holds.

**Labels come from perception, and the active tab's comes from this pass.** The manager learns a tab's title when that tab is perceived, so its record for the tab being looked at right now is one pass behind. Perception already has the current title in hand, so it fills that one in itself. The effect is that the other tabs are as of when they were last seen, which is the best anyone can say without switching to them, and the active one is current.

**The limit is enforced in two places because there are two threats.** An agent asking for a sixth tab is a planning mistake, and it gets a failed action with `TAB_LIMIT_REACHED` that the recovery ladder can work with by closing something. A page opening tabs in a loop is the site fighting back, and it can do that faster than the ladder runs, so a surplus popup is closed rather than tracked. Without the second case the limit is decorative.

**The tab actions are verified against the registry, never the URL.** This is the one that would have been a silent bug. A `new_tab` that failed leaves the old tab active, and if that tab was already on the right host then a declared `url_contains` passes on a page the action never reached. Counting tabs cannot be fooled that way. Switching tabs changes no URL at all, so `url_changed` would fail every successful switch.

**`close_tab` is verified by the tab count, not by the active tab changing.** Closing a background tab correctly leaves the active tab alone. An "active tab changed" check would fail a close that worked perfectly.

**The three tab checks store as one `verification_method`.** Section 4.5 gives six outcome types and the column holds one of them. `actual["check"]` says which of the three actually ran, so a query for tab outcomes finds all three and no migration is needed the next time a check is added. Same precedent as the two URL checks, which both store as `url_contains`.

**`TabSessionManager` is not slotted.** Playwright caches its wrapper for an event handler as an attribute on the object the handler is bound to, so `context.on("page", self._on_page)` raises `AttributeError` from inside the library if the class has `__slots__`. Found by the test suite immediately; worth the comment in the file because the failure names an attribute nobody wrote.

## The prompt: v1 to v2, and what the eval actually proved

`planner_v2.md` is `planner_v1.md` plus one section on tabs. The diff is 33 added lines and zero removed or changed ones, which I checked rather than assumed.

The brief said to make v2 the default only after the eval harness shows no regression. Here are the numbers, both runs against the default mock provider:

| | v1 | v2 |
| --- | --- | --- |
| cases | 22 | 22 |
| action accuracy | 32% | 32% |
| groundedness | 100% | 100% |
| hallucinated index | 0% | 0% |
| unsafe values typed | 0% | 0% |
| tokens in / out | 115 / 80 | 115 / 80 |

**Stated plainly: the eval could not distinguish v1 from v2, so v2 is unvalidated by that harness.** The mock provider ignores the system prompt entirely. Its decisions come from rules over the goal and the page summary, so no change to a prompt file can move these numbers in either direction, and the two columns above are identical by construction rather than by measurement. The run shows one thing only: that v2 loads, the registry resolves it, and nothing outside the prompt regressed. It is not evidence that v2 is an improvement, and it could not have caught v2 being worse.

v2 is the default regardless, and what it rests on is the real-loop coverage rather than the prompt eval: the SkyFare `newtab` journey in the chaos suite drives the whole loop through a real Chromium and asserts the tab machinery the new prompt section describes. The supporting argument is that the diff is purely additive, 33 added lines with nothing removed or reworded, so a regression could only come from added length.

A live run would settle it, and one is deliberately not being spent here: the real numbers come in one go at the benchmark stage rather than in pieces. The command, for when that happens:

```
uv run python scripts/eval_planner.py --provider anthropic --prompt-version v1
uv run python scripts/eval_planner.py --provider anthropic --prompt-version v2
```

The 32% is the mock's own ceiling on this case set, not a regression. The mock's rules are tuned for the SkyFare flow, and most eval cases are other fixture pages with other goals.

## A bug found on the way

`PLANNER_PROMPT_VERSION` was doing nothing outside the eval script. `Planner(llm)` with no registry constructs `PromptRegistry()`, whose default is the literal `"v1"`, and both the task runner and the chaos harness constructed it that way. Setting the version in the environment changed the eval script's behaviour and nothing that runs a real task. Both now pass `PromptRegistry(settings.PLANNER_PROMPT_VERSION)`, which is what made the chaos logs show `prompt_version=v2` instead of `v1`.

That is also the reason the eval comparison above was worth running as two explicit `--prompt-version` runs rather than trusting the setting.

## Viva questions

**Why does the session manager belong outside the driver, when the driver is the only thing that can open a tab?**

Because two other layers need to read it and neither should reach into the driver to do so. Perception needs the tab list and the labels to build the header; the orchestrator needs the active tab id to stamp on every step row and every step event. Before this part the driver held that state privately and exposed pieces of it as properties, so the answer was whatever the driver last happened to record.

The manager also owns a decision the driver has no business making: what "the tab after this one" means when the active tab closes. That is a question about how an agent works, not about how Chromium works.

**A page opens six tabs in a loop. What happens, and what did you consider instead?**

The first however-many fill the limit and the rest are closed as they arrive, with a warning logged. The agent sees five tabs and can carry on.

The alternative I considered was tracking them all and refusing only the agent's own `new_tab`, which is simpler and wrong: the tabs still exist in the context, each one is a live page consuming memory, and a page that wants to exhaust the agent can keep going. Refusing to track them but leaving them open is worse than either, because then the agent is in a browser whose real state it cannot see.

What is not defended against is a page opening and closing tabs fast enough to churn the id counter. That is bounded by the counter being an integer and harmless.

**Why not verify `switch_tab` by checking the URL of the page you ended up on?**

Because both tabs can be on the same URL, and often are: two flight detail pages differing only by a query parameter, or a site that pushes the same path into both. The tab registry answers the question the action actually asked, which is "am I looking at a different tab now", and it answers it from state the driver maintains rather than from a page that may be mid-navigation.

There is a second reason. A URL check on a switch would pass for the wrong reason whenever the destination tab happened to have navigated itself in the background, and fail for the wrong reason whenever the two tabs matched. Neither failure would be readable in the step row afterwards.

## Follow-ups

- The eval harness is single page and single turn, so it cannot score a tab decision: there is only ever one tab when a case starts. Scoring the new prompt section properly needs the harness to accept a setup script, which is a bigger change than this part called for. The multi-tab behaviour is covered by the unit suite and by the SkyFare journey in the chaos suite instead.
- A tab's label is its document title, site suffix included: `SpiceJet SG-419 | SkyFare`. Stripping the suffix would be guessing at a site's title convention.
- `MAX_TABS` is a global per task rather than per depth. A legitimate journey that needs six tabs cannot have them, and would have to close as it goes.
- Nothing prunes the label of a tab whose page navigated without being perceived. The header can therefore name a tab by what it held last time perception saw it, which is stale rather than wrong, and switching to it corrects it on the next pass.
