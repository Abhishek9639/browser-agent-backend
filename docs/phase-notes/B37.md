# B37 - Popups, unnamed inputs and rate limits

## What was built

Fixes found by running one real task, "search internships on Internshala", through the whole stack in Chrome until it stopped failing for reasons in our code.

## Key decisions

The first failure looked like a typing bug. Reproducing it showed three causes in a row: a sign-up popup covering every field, the close button being an unlabelled icon no label match can find, and the planner choosing an unnamed box inside a dropdown widget over the real search field. Each got a deterministic fix (a popup detector, a planner validation with a repair turn) rather than a longer prompt, because a prompt is a request and a check is a guarantee. The verifier's name matching was loosened for the planner's descriptions, then tightened again after a real run showed it matching the wrong control.

The last failure was not ours: Groq's daily token limit asked for a 756 second wait and the retry loop obeyed. A task has a time budget and a person watching it, so a wait beyond 90 seconds now fails fast.

## Viva questions

**1. Why detect a popup from covered elements instead of asking the model to close it?**
The model is shown the elements but not told a popup is why they are unreachable, and its close target may have no label. Counting covered elements and finding a corner icon is deterministic, and the click is limited to dismissals.

**2. Why not click "Accept" to clear a cookie banner?**
Accepting is consent given on the user's behalf. Dismissal is the least destructive reading, so only dismissals are automatic.

**3. Why fail fast on a long rate limit instead of waiting?**
Waiting spends the task's time budget on a quota that will not clear, while the person watches nothing happen. Failing hands the decision to the fallback, or to the user.
