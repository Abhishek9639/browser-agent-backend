# B14 - Planner, prompt registry, eval harness

## What was built

The part that decides. A goal and a page go in, one validated and grounded decision comes out, and a harness measures how often that decision is any good.

- `app/agent/planner/schema.py`, `prompts/planner_v1.md`, `registry.py`, `planner.py`.
- `tests/eval/planner_cases.yaml` and `scripts/eval_planner.py`.
- 71 unit tests.

## Key decisions

**The JSON schema is hand-written, not generated.** `Decision.model_json_schema()` would emit `anyOf` unions for optional fields and omit them from `required`, which provider strict modes reject. More importantly, the schema a model sees *is part of the prompt*: "Never invent an index" belongs in the `targetIndex` description, where the model reads it while filling that field, not only in the system prompt. A test asserts the published properties match the model's fields exactly, so the two cannot drift.

**Cross-field rules raise rather than repair.** A `click` with no `targetIndex` and a `done` with no `finalAnswer` are both schema-valid and both useless. Filling in a blank would execute something nobody chose, so these are validation errors that cost the model its one repair turn.

**Groundedness is a separate guard from schema validation.** The schema cannot express "index 14 exists on this page", because that depends on the page. Checking it here is what makes "never invent an element" enforceable rather than merely requested, and it is the third of the four guards spec section 4.11 lists. The repair message names the indices that *are* available, because telling a model it is wrong without telling it what would be right wastes the turn.

**One repair turn, not zero and not three.** Spec section 4.5 says one. Zero is harsh on a model that made a recoverable slip; three is an expensive way to discover the prompt is wrong. Transport retries are a different mechanism living in `RetryingLLM`, and the planner deliberately does not add its own: a test asserts a provider outage produces one call from here, not two.

**The prompt is a file, and it is versioned.** Prompt changes move behaviour as much as model changes do. Without the version on every `llm_decisions` row there is no way to tell whether this week's better numbers came from a better prompt or an easier page. A file also means a prompt change shows up as a readable diff.

**Stable content first in the prompt.** Goal, then history, then hint, then page state. Only the last part changes every turn. That ordering is what will let prompt caching work when it is added, and a test asserts it so a later edit cannot quietly break the prefix.

## Two things that went wrong

**I spent your API quota by accident.** Running `scripts/eval_planner.py` bare picked up `LLM_PROVIDER=gemini` from `.env` and made real calls until Gemini rate-limited it. The brief said the default provider should be the mock, and it was not: the script deferred to settings. It now hard-defaults to `mock` and ignores `LLM_PROVIDER` entirely, so a bare run cannot spend anything; a live run is opt-in through `--provider`. My mistake, and the fix is the behaviour that was specified in the first place.

**Unit tests were reading the developer's `.env`.** Adding `LLM_PROVIDER=gemini` locally broke two factory tests that assert the committed defaults, while CI stayed green because CI has no `.env`. Tests that depend on whose machine they run on are not tests. An autouse session fixture now points `Settings` away from `.env` and removes any exported variable matching a settings field, and the suite passes with a deliberately hostile environment. This had been latent since the settings module was written; it only surfaced when a local value finally contradicted a default.

## What the eval says

With the mock provider: **22 cases, 32% action accuracy, 100% groundedness, 0% unsafe values, 0 repairs needed.**

The accuracy number is the mock being a keyword matcher that knows one task shape, exactly as recorded in its own known limitations. It is not a measure of the prompt. What the run does establish is that the harness works end to end, that the groundedness guard holds on every case, and that nothing typed a card number into a page.

The number worth having is the same run against a real provider, which is one flag away and costs a few thousand tokens:

```bash
uv run python scripts/eval_planner.py --provider gemini
```

I have not run that, because it spends quota and the earlier accident already spent some without asking.

## Viva questions

**Why check that the index exists, when the provider already constrained the output to the schema?**

Because the schema and the page are different kinds of constraint. A strict decode guarantees the answer is an object with an integer `targetIndex`; it cannot guarantee that 14 is an element on *this* page, because the schema does not know the page. So a model can return a perfectly schema-valid decision naming an element that was never shown to it, either because it hallucinated, or because it worked from a stale summary, or because page text persuaded it something was there.

That check is also the hinge of the injection defence. The collector deliberately withholds hidden elements, and the planner can only name an index it was given. Together those mean an injected control cannot be targeted even if the model wants to: it has no index to name. Without the existence check, withholding the element would achieve nothing.

**The prompt tells the model page content is untrusted. Why is that not just theatre, given a model can be persuaded?**

On its own it would be close to theatre, which is why it is one of four layers rather than the defence. The prompt raises the cost of a naive attack. The fence around `<page_state>` means an injected "ignore previous instructions" arrives clearly labelled as data. The schema, the action allow-list, the index check and the risk policy then hold regardless of whether the model was persuaded: a model fully convinced it should wire money still cannot emit an action outside twelve names, cannot target an element it was not shown, and cannot execute anything irreversible without a human approving it.

The prompt instruction is the layer that helps when the others are silent, which is the case of a *visible* button whose label is an instruction. There the element is legitimately targetable and the action is legitimately in the allow-list, so the only thing standing between the page and the agent is the model having been told that a button's label is not an order.

**The eval scores against a set of acceptable answers rather than one. Does that not make it too easy to pass?**

It makes it measure the right thing. On a half-filled form, typing into either empty field is correct; insisting on one would score obedience to my ordering rather than competence. A single golden answer per case would also make the numbers brittle, dropping whenever a fixture changed or the model chose a different reasonable route, which trains you to stop trusting the eval.

Where being wrong is genuinely unsafe rather than merely unhelpful, the case pins it: four cases assert `requiresApproval` exactly, and the scorer separately flags any decision that typed a known secret from the payment fixture, independent of whether the action matched. Those checks have one right answer because there is one.

## Planned optimisation: prompt caching

Carried forward from the provider work and now actionable, because the prompt exists. The system prompt and the decision schema are byte-identical on every step; the history and page state are not. The message order already puts the stable parts first, which is the prerequisite. What remains is a per-provider cache breakpoint behind the adapter interface, and a check that the hit rate is actually non-zero, since caching silently does nothing if the prefix varies.

## Follow-ups

- Nothing calls `Planner` yet; the orchestrator owns the loop.
- A `Decision` is not yet convertible into a browser action. The mapping is mechanical but it belongs with the code that executes it, and it is where the action allow-list guard will sit.
- `needsVision` and low confidence are recorded but nothing acts on them until the grounding step exists.
- The eval uses one prompt version. `--prompt-version` is wired so two can be compared once there is a second.
